# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

## Project

Gods is a Bukkit/Spigot plugin. Players build altars, pray to gods they name themselves, and gain powers, quests, holy lands (land protection), marriages, holy books and so on. It runs on Spigot and Paper 26.1+ with Java 25 (`api-version: '1.21'` in `plugin.yml`). It compiles against `paper-api` 26.3 but **must keep running on Spigot**: use only Bukkit/Spigot API, and reach Paper-only API behind a runtime check. WorldGuard and PlaceholderAPI are optional (softdepend).

## Build & test

```bash
nix develop                           # devshell with JDK 25 + Maven (flake.nix); or prefix commands with `nix develop -c`
mvn clean package                     # default goal; tests and builds plugin/target/Gods-<version>.jar
mvn test -pl plugin -am -Dtest=SettingsLoaderTest -Dsurefire.failIfNoSpecifiedTests=false  # one test class (append #method for one test)
mvn -Pspigot -pl plugin -am clean compile  # compile against spigot-api instead: fails on any Paper-only API (CI runs this too)
```

- A parent `pom.xml` (shared versions and repositories) with the `plugin/` module (`gods`), in the standard Maven layout: `plugin/src/main/java`, `plugin/src/main/resources`, `plugin/src/test/java`. Only `plugin.yml` is Maven-filtered (for `${project.version}`).
- Java 25 (`maven.compiler.release`). CI (`.github/workflows/build.yml`) builds on JDK 25 for every push and PR. Pushing a tag `v<pom version>` (e.g. `v1.0.0`) publishes a GitHub release with the jar.
- JUnit tests (`plugin/src/test/java`, no server needed) cover config loading and migration, the data file storage, the repositories (each reads a realistic old file from `plugin/src/test/resources/legacy/`, saves it and reads it back unchanged), the data migrations and the message files (`LegacyText`, `LegacyLangFiles`: the old bundled files convert to exactly the new ones and customized ones keep their changes; `MessageKeysTest`; `MessagesTest`), the pure rules of the services (`BelieverRules`, `GodRules`, `MoodRules`, `RelationRules`, `PriestRules`, `BlessingRules`, `SacrificeRules`, `QuestRules`, `HolyPowerRules`, `PowerCooldowns`, `HolyArtifactRules`, `HolyLandContest`, `AltarSigns`, `RegionKey`, `ActionCooldown`) and the command router (`CommandRouterTest`, `PluginYmlTest`); test fixtures are in `plugin/src/test/resources`. Most game behavior can only be checked by running the jar on a server.
- `Biome`, `Sound` and other former enums are registry interfaces now: compare with `==`, never `switch` on them or call `valueOf`.

## Architecture

**Entry point and lifecycle:** `com.dogonfire.gods.Gods` (the `JavaPlugin`) only wires things.
- `onEnable` reads `config.yml` into `Settings` (and disables the plugin if it can't, so no data file is overwritten), creates `Storage` and the `GodsContext`, loads the data in `loadData()` (holy books, marriages, holy land if enabled → messages (after converting old language files) → gods (`GodService`) → quests → believers → god white/blacklist), registers the `/g` command (alias `/gods`, `registerCommands()`) and the always-on listeners (`GodListener`, `BelieverListener`, `AltarListener`, `ChatListener`, in that order), the PlaceholderAPI expansion, the repeating tasks (the gods' turns `task/GodUpdateTask`, autosave, chat cache refresh; kept in `tasks`), and then calls `startFeatures()`.
- `startFeatures()`/`stopFeatures()` register and unregister what config.yml switches on and off (now: `QuestListener`, `HolyBookListener` and `HolyArtifactListener` while quests, bibles and holy artifacts are enabled, then `HolyLandListener` and `MarriageListener` while holy land and marriage are; the order matters for handlers of the same event and priority). Put a new switchable listener or repeating task there, through `registerFeature` or a tracked `BukkitTask`, so reload never doubles it.
- `/g reload` (`Gods.reload()`): reads `config.yml` again (if that fails the old settings and data stay), then `Storage.prepareReload` waits for pending writes and lets each data file decide: one edited on disk since Gods last read or wrote it (or that couldn't be read) is read again, dropping changes not yet saved, so a hand edit wins; every other file keeps what is in memory and is saved. Then `stopFeatures()`, `loadData()` (message files, and the data files: `DataFile.load()` / `Repository.load()` keep the data in memory when `lastLoadKept()`), `startFeatures()`, `Storage.finishReload()`.
- `onDisable` unregisters the PlaceholderAPI expansion, stops the features, cancels the tasks (and every delayed task), and `Storage.close()` writes what changed and waits for it.
- New persistent data gets a model, a repository and a service (see "Models, repositories and services"); add the service to `GodsContext` and `loadData()`.

**Object graph (`GodsContext`):** there are no singletons and no static way to reach the plugin. `GodsContext` is built once per enable and owns `Storage`, `Messages` and every service (`ctx.godService()`, `ctx.believerService()`, …, `ctx.plugin()`, `ctx.storage()`, `ctx.worldGuard()`); services, listeners, commands (`SubCommand.ctx`) and tasks (`Task.ctx`) get it through their constructor and keep it in a `ctx` field. The services call each other in cycles, so they keep the context and ask it for the others at use time; a service gets its repository from `Storage` through its constructor. Constructors must not call other services (the graph is still being built). Every service exists even when its feature is off (its data file is then not loaded): check the setting before using a feature's service. A helper that needs the plugin takes it as a parameter (e.g. `new HolyBookItem(plugin, item)`).

**Storage (`storage/`):** `Storage` owns the data files (`gods.yml`, `believers.yml`, `quests.yml`, `holyland.yml`, `marriages.yml`, `bibles.yml`, `whitelist.yml`, `blacklist.yml`), one `DataFile` each held by its `Repository` (`gods()`, `believers()`, `quests()`, `holyLands()`, `marriages()`, `bibles()`, `whitelist()`, `blacklist()`; see below), and the single background thread that writes them. `Storage` also takes a name → UUID lookup (the server's known players), only used to upgrade priests old `gods.yml` files keep by name.
- A service calls its repository's `load()` in its own `load()` and after a change calls `markDirty()` (written by the next autosave, every 3 minutes, on reload and on disable) or `save()` (written now). Never write a data file any other way.
- A flush takes the YAML text on the main thread and writes it on the storage thread through a temp file and an atomic move, so the main thread never waits for the disk and a crash never leaves half a file.
- A file that can't be read is copied to `<file>.broken-<timestamp>`, logged, and is read-only until a later load works: it is never written over. The first load then starts empty, a reload keeps what was in memory. The old `!!java.util.UUID` tags of `gods.yml` are repaired on load (`Storage.UUID_TAGS`).
- `Storage` takes its writer as an `ExecutorService`, so `StorageTest` runs it without a server.
- A `DataFile` can carry a data version (a `VersionedYaml`, now `gods.yml` and `holyland.yml`, both `data-version: 2`): an older file is copied to `<file>.v<n>.bak` (a second backup of the same version gets a timestamp, so none is ever overwritten), upgraded through its `Migration`s on load and written back at once by its repository. A file that can't be upgraded is used as it is but never written.

**Models, repositories and services** (every domain):
- `model/` holds plain data objects with typed fields (`Instant` for times, `UUID` for players): `God` (with `GodHome`, `ContestedLand`; and the enums `GodType`, `GodGender`, `GodMood`), `Believer`, `HolyLand`, `NeutralLand`, `RegionKey`, `Marriage` (one player's proposal, engagement or marriage), `MarriedCouple`, `Quest` (with `QuestLocation`, `QuestTarget` and the enum `QuestType`), `HolyBook`, and the enum `HolyPower`. They have no logic and don't save themselves.
- `storage/` has one `Repository` per file (`GodRepository`, `BelieverRepository`, `HolyLandRepository`, `MarriageRepository`, `QuestRepository`, `HolyBookRepository` for bibles.yml, `GodListRepository` for whitelist.yml and blacklist.yml). `load()` reads the `DataFile`'s YAML into models; after that the models are the truth, and each flush asks the repository for a fresh YAML snapshot (`write`) on the main thread. The files keep the keys and the time formats they always had (`util/LegacyDates`: `"HH:mm:ss dd-MM-yyyy"`, holy land and quests `"HH:mm dd-MM-yyyy"`, server time zone): a time that can't be parsed reads as never. Keys a repository doesn't know are written back unchanged: top-level ones (e.g. entries keyed by player name in very old files) through `keepUnknown`, those inside an entry through the model's `extras`.
- `service/` owns every change. The gods (all on `GodRepository`, one `gods.yml`):
  - `GodService`: creating and removing gods, which gods exist and have a believer online, type/gender/color/title/voice, seed and verbosity, power (from the believers), description, home, access, holy land PvP/mob settings, last quest time; it loads `gods.yml`.
  - `MoodService`: mood, pleased/angry modifiers, falloff. `RelationService`: alliances and wars, and the attacker's side of an attack on holy land (`HolyLandService` owns the land's side).
  - `PriestService`: priests (dropped when they stop praying), priest offers and answers, assign/remove with the configured console commands, reminders. `BlessingService`: blessings and curses on players (effects, items, healing, holy artifacts, lightning, mobs) and a god's blessed/cursed player. `CommandmentService`: holy/unholy food and mobs, eating and killing, sacrifices and sacrifice needs. `PrayerService`: praying at altars (creating the god), joining/changing god, `/g yes`/`/g no`, leaving, dying, lost believers.
  - `GodSpeech`: a god's words (`say`, `sayToBelievers`, …, `GodSpeakTask`) and the delayed info messages (`sendInfo`, `InfoTask`); see "Messages".
  - `task/GodUpdateTask` (every 200 ticks, started by `Gods`) gives one god with a believer online its turn and decides when the services act.

  Quests, holy books, holy artifacts and powers:
  - `QuestService` (on `QuestRepository`, `quests.yml`, loaded always): making a new quest, counting progress when believers act (`handleKilledMob`, `handleSacrifice`, `handleReadBible`, `handleOpenChest`, …), completing and failing quests, rewards, and the quest speech table (`Phase` → `Voice` per `QuestType`). `QuestRules` has the numbers (sizes, durations, targets, expiry, reward rolls, holy names, pilgrimage spots), drawn from the `Random` in the order the old code drew them; `PilgrimageSites` finds, places and removes pilgrimage chests.
  - `HolyBookService` (on `HolyBookRepository`, `bibles.yml`, loaded while bibles are enabled): each god's book (a default one written from its commandments when first needed), copies, editable copies, `/g setbible`, and which god a book belongs to. `HolyBookItem` wraps the book item.
  - `HolyArtifactService` (no data file; the state is in the item's tags): making an artifact for a god type, recognizing one, using one (uses, rank, wear). `HolyArtifactRules`: rank names and lore lines.
  - `HolyPowerService`: cooldowns (`PowerCooldowns`, per player and power, and one sky power per world at a time) and starting a power; the powers are in `service/power/` by kind (`SkyPowers`, `GiftPowers`, `NaturePowers`, `AttackPowers`). `HolyPowerRules`: each power's lore text (`describe`) and reading it back from old artifacts (`parse`), cooldowns, effect radius.

  The others: `BelieverService` (gods, prayers, prayer power, chat mode, invitations, priest offers, blessing cooldowns), `HolyLandService` (claims, neutral land, attacks on holy land), `MarriageService`, `GodListService` (`isAllowedGod`, the whitelist's minimum power), `AltarService` (altar blocks and signs, dropped items for sacrifices; no data file), `ChatService` (religion chat and the thread-safe snapshot for the chat thread and PlaceholderAPI), `Permissions` (Bukkit's permission check), `Titles` (screen titles, through `TitleSendEvent`). A service changes the model, then calls `repository.markDirty()` (next autosave) or `repository.save()` (now; holy lands and marriages always did). Rules that need no server are pure static helpers next to them (`GodRules`, `MoodRules`, `RelationRules`, `PriestRules`, `BlessingRules`, `SacrificeRules`, `BelieverRules`, `QuestRules`, `HolyPowerRules`, `HolyArtifactRules`, `HolyLandContest`, `AltarSigns`) and are what the tests cover. Keep a service to one area; a new one goes in `GodsContext` (with its repository from `Storage`) and, if it loads a file, in `loadData()`.
- `gods.yml` keeps one section per god name with the keys Gods always wrote (`DivineForce`, `Gender`, `Home.X`, `Priests` as UUID strings, `SacrificeValues.<material>`, …, see `GodRepository`); values it can't read (an unknown god type) and unknown keys are kept. Version 1 (0.9.x and this branch before data versions) is upgraded by `GodsV1ToV2`: `PriestName` and priests kept by name become UUIDs (unknown names are dropped and logged; the `.v1.bak` keeps them) and `LanguageFileName` goes.
- Holy land is stored per 128x128 region and world (`RegionKey`): `Holylands.<world key>.<hash>` / `NeutralLands.<world key>.<hash>`, with `hash = ((long) regionX << 32) | (regionZ & 0xFFFFFFFFL)` and the world key the world name with `.` replaced by `_`. `HolyLandsV1ToV2` drops the 0.9.x `Holyland` / `NeutralLand` sections, whose hash can't be converted.
- `quests.yml` (no data version, the format never changed) keeps one section per god (`Type` as `"Pilgrimage"`, `Amount`, `TargetType`, `MaxDuration`, `Progress`, `Players` as UUID strings, `CreatedTime`, `Location.World/X/Y/Z/Ground`) and `QuestTargets.<hash>` (`God`, `Location`), with the hash `x * 73856093 ^ y * 19349663 ^ z * 83492791` (`QuestTarget.keyFor`). A missing `Amount`/`Progress`/`Players` stays missing. Loading drops what 0.9.x left that can't be used (the `Global` section, HOLYWAR/SLAYDRAGON/GETHOLYARTIFACT/PVPREVENGE quests and their targets) and writes the file back. `bibles.yml` keeps `<god>.Title`, `.Author`, `.Pages`.
- To add data: add the field to the model, read and write it in the repository with a new key (keep it a string, number, boolean, list or map), and change it only through the service. Renaming or reshaping existing keys needs a data version: give the file a `VersionedYaml` in `Storage` (or bump its version), add a `Migration` in `migration/` and a test with an old file. A new file gets a `DataFile` and a `Repository` subclass in `Storage`, added to `Storage.files`.

**Settings (`config/`, `migration/`):** `config.yml` is bundled (`plugin/src/main/resources/config.yml`), commented, in kebab-case sections, with a `config-version` (now `2`, `Gods.CONFIG_VERSION`). Gods never rewrites it except to upgrade it or to add missing settings, so admins keep their comments and layout.
- Loading (`Gods.loadSettings`): the bundled file is written on first start; `VersionedYaml` upgrades an older file through the `Migration` chain (keeping `config.yml.v<n>.bak`, writing atomically through `util/AtomicFiles`); `ConfigDefaults.addMissing` adds settings a newer bundled config has (entries of the free-form sections `altars.block-types` and `quests.reward-values` that an admin removed stay removed); then `SettingsLoader` builds `Settings` with the bundled file as defaults.
- `Settings` is an immutable record tree, one record per section (`settings.blessings().blessedSeconds()`), with unmodifiable collections and parsed types (`Material`, `GodType`). `SettingsLoader` validates: a value of the wrong type is logged with its key and gets the bundled default, numbers are clamped, unknown blocks/items/god types are logged and skipped. Nothing pushes settings into services.
- Code reads settings through `ctx.settings()` (or `Gods#settings()`) every time (never keep a `Settings` or a value from it), so `/g reload` takes effect by swapping that one object.
- `ConfigV1ToV2` upgrades configs from Gods 0.9.x and from this branch before config versions (`Settings.Debug`, `Blessing.MaxBlessingTime`, …): it copies each old key's value into the bundled config (the `MOVED` table, plus the altar, reward and breakable-block lists), and drops obsolete keys (`OBSOLETE`) and warns about unknown ones.
- To add a setting: add the key with its default and a comment to `config.yml` (put the unit in the key name: `-seconds`, `-minutes`, `-hours`, `-days`), add a record component and its read in `SettingsLoader` (with a range check), and read it through `ctx.settings()`. Existing servers get it from `ConfigDefaults` without a version bump. Renaming or moving a key, or changing its meaning, needs `CONFIG_VERSION` + 1 and a new `Migration` (`ConfigV2ToV3`) registered in `Gods.loadSettings`, with a test in `ConfigV1ToV2Test`'s style. `BundledConfigTest` checks the defaults (update `oldDefaults()` when you add one) and that every setting has a comment.

**Quests:** only PILGRIMAGE, SLAY, ITEMSACRIFICE and GIVEITEMS are generated; the other `QuestType`s stay in the enum because old `quests.yml` files may hold them. Location searches (pilgrimage chests, `PilgrimageSites`) have a hard cap on attempts and on chunks they load: never loop until a spot is found.

**Data rules:** players are keyed by **UUID**; never key data by player name. Never write a raw `UUID` (or any other non-primitive object) into a `YamlConfiguration`: SnakeYAML tags it and Bukkit then refuses to load the file. Store `toString()`.
- Holy books and holy artifacts are recognized by `PersistentDataContainer` tags (`gods:holy_book_god`, `gods:holy_power`, …), never by display name or lore; old untagged items are only a fallback.
- Permission checks go through `ctx.permissions().hasPermission`, which is Bukkit's `Player#hasPermission`. There is no Vault dependency.

**Commands (`command/`):** `CommandRouter` (a `TabExecutor`) handles `/g` (alias `/gods`); each subcommand is its own `SubCommand` class (`<What>Command`), registered in `Gods.registerCommands()`. `/g` alone shows `Overview`. The router finds the command by its first argument (name or alias, ignoring case; unknown: `command.invalid`) and checks, in this order, before `execute(sender, args)` (`args` = what follows the name): the feature is on (`disabledMessage()`, e.g. `command.disabled.marriage`; null when on), the permission (ops have all, players through `ctx.permissions()`, the console through Bukkit; `command.no-permission`), player-only (`command.player-only`), priest-only (the command's own `not-priest` message or `command.priest-only`), believer-only (`command.no-god` or the command's own) and `args(min, max)` (`command.usage` with `command.<name>.parameters`). So a player-only command can cast `sender` to `Player`, and a believer-only one can call `believersGod(player)`. `execute` stops with `throw new CommandException("command.<name>.<reply>", tags…)` (sent to the sender) or `throw new UsageException()`. `/g help` (`HelpCommand`) and tab completion of the first argument list what `router.canUse` allows (feature on, permission, player, priest); later arguments come from `tabComplete(sender, args)`. Shared helpers are on `SubCommand`: `onlinePlayer(name, notFoundKey)` (exact name, online), `knownBeliever(god, name)` (a god's believer, online or not, without asking Mojang), `onlinePlayerNames`, `believerNames`, `godNames`, `nameOf(uuid)`, `timeAgo`. Commands call services and pass `Player`/`UUID`, never player names. `CommandChecks` is the router's only link to believers and priests, so `CommandRouterTest` runs the router with fake commands and proxy senders; `PluginYmlTest` checks every command's permission is declared and a child of `gods.*`. To add a command:
1. Write `XCommand extends SubCommand`: the constructor calls `super(ctx, "name", "gods.node")` and then `playerOnly()` / `believerOnly()` / `priestOnly(…)` / `args(min, max)` / `aliases(…)` as needed; override `disabledMessage()` if a config switch turns it off, and `tabComplete` for its arguments.
2. Add it to `Gods.registerCommands()`.
3. Add `command.<name>.parameters`, `.description` and its replies to `lang/english/messages.yml` (`MessageKeysTest` checks them).
4. Declare its permission node in `plugin/src/main/resources/plugin.yml` and as a child of `gods.*`.

**Messages (`message/`, MiniMessage):** no user-visible text belongs in Java code; log and console-only text stays English in code. Everything players see comes from `plugins/Gods/lang/<language>/` (`general.language` in config.yml; only `english` is bundled):
- `messages.yml`: every message that isn't a god's voice, in sections by area (`command.<name>.*` incl. `.parameters`/`.description` for `/g help`, `holy-land.*`, `altar.*`, `prayer.*`, `artifact.*`, `broadcast.*`, `names.*` for item/mob/god type/gender/mood names, …) and `god.speech`, the format of a god's words. A message is one line, a list of lines, or `''` (send nothing).
- `voices/<type>_<gender>.yml` (26 files, e.g. `voices/sun_female.yml`): a god's voice. Each key (a `Voice`, e.g. `believers-slay-quest-started`; the old LANGUAGESTRING name without `GodTo`, kebab case) is a list of lines; the god says one at random; `''`/`[]` says nothing. The voice is picked per god from its type and gender (`GodService.getVoiceForGod`, `GodRules.voice`).
- Both carry `messages-version` (`Messages.MESSAGES_VERSION`, now 2). A key missing from the server's file falls back to the bundled file of the same language, then to the bundled english one (a voice never falls back to another type's voice). Missing bundled files are copied to the server.
- `Messages` (`ctx.messages()`, loaded by `loadData()` on enable and `/g reload`) renders MiniMessage to legacy `§` text: `send(sender, key, tags…)`, `legacy`/`legacyLines`/`component(key, tags…)`, `broadcast(server, key, tags…)`, `parse(miniMessage)`, and the names `itemName`, `mobName`, `godTypeName`, `genderName`, `moodName`. It is thread-safe (the chat thread renders too). Every message knows `<server>` and `<hl>…</hl>` (the gold, not bold highlight the old `$`-placeholders had). Tag helpers: `Messages.text(name, value)` (unparsed), `player`, `god`, `amount`, `type`, `displayName`/`legacyText` (text with `§` colors, e.g. display names), `component`, `color(name, ChatColor)`. **Values from players (names, god names, descriptions, chat) must go in unparsed** through these helpers, never by string concatenation into MiniMessage.
- `GodSpeech` (`ctx.godSpeech()`) is the god's voice: `say`/`sayWithQuestion(god, player, Voice, delay, tags…)`, `sayToBeliever(s)`, `sayToBelieversExcept`, `sayToPriests`; `sayText` makes a god say any MiniMessage text in its style; `voiceLine`/`plainVoiceLine` pick a line (book pages). A god's line knows `<god>`, and `<player>` is the player spoken to unless the call passes one. Every utterance passes `GodSpeech.deliver`: that is where a `GodSpeakEvent` belongs. `sendInfo(player, key, delay, tags…)` sends a messages.yml message later (`InfoTask`). Every call passes its own tags; there is no shared placeholder state.
- **Adventure rules:** MiniMessage and the legacy serializer are shaded and relocated to `com.dogonfire.gods.libs.kyori` (Spigot has no Adventure). Never pass Adventure objects to Bukkit/Paper API, and never call Adventure methods on Bukkit objects: after relocation they are different classes. Text reaches Bukkit as legacy strings (`Messages.legacy`): chat, titles, item names and lore, book pages, signs, broadcasts.
- To add a message: add the key with a comment listing its tags to `lang/english/messages.yml` and use `send(…, "the.key", …)`. To add a voice situation: add a `Voice` and a list of lines to **all 26** `lang/english/voices/*.yml`. `MessageKeysTest` checks that every key the code names exists (it scans string literals of the form `"section.key"`), that every command has its parameters and description, and that every `Voice` is in every voice file. New keys reach servers through the bundled fallback; renaming or moving keys needs `MESSAGES_VERSION` + 1 and a migration.
- Old files: `migration/LegacyLangFiles` converts the language files of 0.9.x and of this branch before MiniMessage (`lang/<language>_general.yml`, `lang/<language>_<type>_<gender>.yml`) on every load: each becomes the new file (the bundled one plus every message the old file says differently, converted by `LegacyText`: `&`/`§` codes to MiniMessage, `$PlayerName` & co. to the key's tags, old keys to new ones), and the old file is moved to `lang/old/`. An existing new file is never overwritten.
- Altar sign words ("Altar / of", "Curses / On", "Blessings / On") are not messages: they mark altars in the world, so they stay in `AltarSigns`. Old untagged holy artifacts are read by their English lore (`HolyPowerRules.describe`, `HolyArtifactRules.isArtifactLine`), whatever `artifact.*` says now.

**Tasks (`task/`):** short delayed `Runnable`s named `<What>Task` (subclasses of `Task`, which takes the context) scheduled through the Bukkit scheduler (divine effects, messages, mob spawns), and `GodUpdateTask`, the gods' update loop. Repeating ones must end on their own (a stop time, the player logging off); onDisable cancels whatever is left. A task that runs for the life of the plugin belongs in `Gods` (tracked, see lifecycle).

**Integrations (`integration/`):** `GodsPlaceholderExpansion` (PlaceholderAPI, registered only if that plugin is present, unregistered on disable) and `WorldGuardIntegration` (`ctx.worldGuard()`, null without WorldGuard). Each references the other plugin's classes, so only create it when that plugin is there. `GodsMetrics` sends anonymous statistics to bStats (project 35252) with Gods' own charts (`gods`, `believers`, `god_types`, `features`, `language`, `integrations`; the chart ids must match the ones on the bStats project page). bStats asks for chart values on its own thread, so they come from a snapshot `GodsMetrics.refresh()` takes on the main thread (every 5 minutes and after /g reload). bStats is shaded and relocated to `com.dogonfire.gods.libs.bstats`.

**Listeners (`listener/`)** turn events into service calls, one class per area: `HolyLandListener` (protection, entering land, attacks), `AltarListener` (altar signs, praying/cursing/blessing at altars, sacrifices), `BelieverListener` (a believer's death), `MarriageListener` (wedding tokens), `ChatListener` (religion chat, on the async thread through the `ChatService` cache), `GodListener` (commandments on kills and meals, the online gods list on join/quit), `QuestListener` (kills and meals for quests, pilgrimage chests), `HolyBookListener` (reading a holy book) and `HolyArtifactListener` (using one, picking up a second). `GodListener` and `QuestListener` handle meals and share one `ActionCooldown` with `HolyBookListener` (10 seconds; `Gods` owns it), which gives every listener the same answer for the same event. Keep the priorities and `ignoreCancelled` flags when moving a handler, and register a switchable one in `startFeatures`.

**Other:** `changelog.txt` (release notes, newest first).
