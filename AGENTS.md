# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

## Project

Gods is a Bukkit/Spigot plugin. Players build altars, pray to gods they name themselves, and gain powers, quests, holy lands (land protection), marriages, holy books and so on. It runs on Spigot and Paper 26.1+ with Java 25 (`api-version: '1.21'` in `plugin.yml`). It compiles against `paper-api` 26.3 but **must keep running on Spigot**: use only Bukkit/Spigot API, and reach Paper-only API behind a runtime check. WorldGuard and PlaceholderAPI are optional (softdepend).

## Build & test

```bash
nix develop                           # devshell with JDK 25 + Maven (flake.nix); or prefix commands with `nix develop -c`
mvn clean package                     # default goal; tests and builds plugin/target/Gods-<version>.jar
mvn test -pl plugin -am -Dtest=SettingsLoaderTest -Dsurefire.failIfNoSpecifiedTests=false  # one test class (append #method for one test)
mvn -Pspigot -pl plugin -am clean compile  # compile against spigot-api instead: fails on any Paper-only API (CI runs this too)
```

- A parent `pom.xml` (shared versions and repositories) with the `plugin/` module (`gods`), in the standard Maven layout: `plugin/src/main/java`, `plugin/src/main/resources`, `plugin/src/test/java`. Only `plugin.yml` is Maven-filtered (for `${project.version}`).
- Java 25 (`maven.compiler.release`). CI (`.github/workflows/build.yml`) builds on JDK 25 for every push and PR. Pushing a tag `v<pom version>` (e.g. `v1.0.0`) publishes a GitHub release with the jar.
- JUnit tests (`plugin/src/test/java`, no server needed) cover config loading and migration, the data file storage, the repositories (each reads a realistic old file from `plugin/src/test/resources/legacy/`, saves it and reads it back unchanged), the data migrations and the pure rules of the services (`BelieverRules`, `GodRules`, `MoodRules`, `RelationRules`, `PriestRules`, `BlessingRules`, `SacrificeRules`, `HolyLandContest`, `AltarSigns`, `RegionKey`, `ActionCooldown`); test fixtures are in `plugin/src/test/resources`. Most game behavior can only be checked by running the jar on a server.
- `Biome`, `Sound` and other former enums are registry interfaces now: compare with `==`, never `switch` on them or call `valueOf`.

## Architecture

**Entry point and lifecycle:** `com.dogonfire.gods.Gods` (the `JavaPlugin`) only wires things.
- `onEnable` reads `config.yml` into `Settings` (and disables the plugin if it can't, so no data file is overwritten), creates `Storage` and the `GodsContext`, loads the data in `loadData()` (HolyBook, Marriage, HolyLand if enabled → Language → gods (`GodService`) → Quest → Believer → god white/blacklist), registers the `/g` command (alias `/gods`) and the always-on listeners (`GodListener`, `QuestAndHolyItemListener`, `BelieverListener`, `AltarListener`, `ChatListener`, in that order), the PlaceholderAPI expansion, the repeating tasks (the gods' turns `task/GodUpdateTask`, autosave, chat cache refresh; kept in `tasks`), and then calls `startFeatures()`.
- `startFeatures()`/`stopFeatures()` register and unregister what config.yml switches on and off (now: `HolyLandListener` while holy land is enabled, `MarriageListener` while marriage is enabled). Put a new switchable listener or repeating task there, through `registerFeature` or a tracked `BukkitTask`, so reload never doubles it.
- `/g reload` (`Gods.reload()`): reads `config.yml` again (if that fails the old settings and data stay), then `Storage.prepareReload` waits for pending writes and lets each data file decide: one edited on disk since Gods last read or wrote it (or that couldn't be read) is read again, dropping changes not yet saved, so a hand edit wins; every other file keeps what is in memory and is saved. Then `stopFeatures()`, `loadData()` (language files, and the data files: `DataFile.load()` / `Repository.load()` keep the data in memory when `lastLoadKept()`), `startFeatures()`, `Storage.finishReload()`.
- `onDisable` unregisters the PlaceholderAPI expansion, stops the features, cancels the tasks (and every delayed task), and `Storage.close()` writes what changed and waits for it.
- New persistent data gets a model, a repository and a service (see "Models, repositories and services"); add the service to `GodsContext` and `loadData()`.

**Object graph (`GodsContext`):** there are no singletons and no static way to reach the plugin. `GodsContext` is built once per enable and owns `Storage`, every manager and every service (`ctx.godService()`, `ctx.believerService()`, …, `ctx.plugin()`, `ctx.storage()`, `ctx.worldGuard()`); managers, services, listeners, commands (`GodsCommand.ctx`) and tasks (`Task.ctx`) get it through their constructor and keep it in a `ctx` field. The managers and services call each other in cycles, so they keep the context and ask it for the others at use time; a service gets its repository from `Storage` through its constructor. Constructors must not call other managers or services (the graph is still being built). Every manager and service exists even when its feature is off (its data file is then not loaded): check the setting before using a feature's manager or service. A static helper that needs the plugin takes it as a parameter (e.g. `new HolyBook(plugin, item)`).

**Storage (`storage/`):** `Storage` owns the data files (`gods.yml`, `believers.yml`, `quests.yml`, `holyland.yml`, `marriages.yml`, `bibles.yml`, `whitelist.yml`, `blacklist.yml`), one `DataFile` each, and the single background thread that writes them. `gods()`, `believers()`, `holyLands()`, `marriages()`, `whitelist()` and `blacklist()` return the file's `Repository` (see below); the others (`quests()`, `bibles()`) still return the raw `DataFile`. `Storage` also takes a name → UUID lookup (the server's known players), only used to upgrade priests old `gods.yml` files keep by name.
- A manager with a raw `DataFile` calls `file.load()` in its `load()`, works on `file.yaml()` (main thread only; fetch it every time, a load replaces it), and after a change calls `markDirty()` (written by the next autosave, every 3 minutes, on reload and on disable) or `save()` (written now). Never write a data file any other way.
- A flush takes the YAML text on the main thread and writes it on the storage thread through a temp file and an atomic move, so the main thread never waits for the disk and a crash never leaves half a file.
- A file that can't be read is copied to `<file>.broken-<timestamp>`, logged, and is read-only until a later load works: it is never written over. The first load then starts empty, a reload keeps what was in memory. The old `!!java.util.UUID` tags of `gods.yml` are repaired on load (`Storage.UUID_TAGS`).
- `Storage` takes its writer as an `ExecutorService`, so `StorageTest` runs it without a server.
- A `DataFile` can carry a data version (a `VersionedYaml`, now `gods.yml` and `holyland.yml`, both `data-version: 2`): an older file is copied to `<file>.v<n>.bak` (a second backup of the same version gets a timestamp, so none is ever overwritten), upgraded through its `Migration`s on load and written back at once by its repository. A file that can't be upgraded is used as it is but never written.

**Models, repositories and services** (gods, believers, holy lands, marriages, the god white/blacklist and altars so far; quests, holy books, holy artifacts and powers are still managers):
- `model/` holds plain data objects with typed fields (`Instant` for times, `UUID` for players): `God` (with `GodHome`, `ContestedLand`; and the enums `GodType`, `GodGender`, `GodMood`), `Believer`, `HolyLand`, `NeutralLand`, `RegionKey`, `Marriage` (one player's proposal, engagement or marriage), `MarriedCouple`. They have no logic and don't save themselves.
- `storage/` has one `Repository` per file (`GodRepository`, `BelieverRepository`, `HolyLandRepository`, `MarriageRepository`, `GodListRepository` for whitelist.yml and blacklist.yml). `load()` reads the `DataFile`'s YAML into models; after that the models are the truth, and each flush asks the repository for a fresh YAML snapshot (`write`) on the main thread. The files keep the keys and the time formats they always had (`util/LegacyDates`: `"HH:mm:ss dd-MM-yyyy"`, holy land `"HH:mm dd-MM-yyyy"`, server time zone): a time that can't be parsed reads as never. Keys a repository doesn't know are written back unchanged: top-level ones (e.g. entries keyed by player name in very old files) through `keepUnknown`, those inside an entry through the model's `extras`.
- `service/` owns every change. The gods (all on `GodRepository`, one `gods.yml`):
  - `GodService`: creating and removing gods, which gods exist and have a believer online, type/gender/color/title/language file, seed and verbosity, power (from the believers), description, home, access, holy land PvP/mob settings, last quest time; it loads `gods.yml`.
  - `MoodService`: mood, pleased/angry modifiers, falloff. `RelationService`: alliances and wars, and the attacker's side of an attack on holy land (`HolyLandService` owns the land's side).
  - `PriestService`: priests (dropped when they stop praying), priest offers and answers, assign/remove with the configured console commands, reminders. `BlessingService`: blessings and curses on players (effects, items, healing, holy artifacts, lightning, mobs) and a god's blessed/cursed player. `CommandmentService`: holy/unholy food and mobs, eating and killing, sacrifices and sacrifice needs. `PrayerService`: praying at altars (creating the god), joining/changing god, `/g yes`/`/g no`, leaving, dying, lost believers.
  - `GodSpeech`: every message to players, a god's words (`say`, `sayToBelievers`, …, `TaskGodSpeak`) and info messages (`sendInfo`, `TaskInfo`); the one seam the move to MiniMessage changes. Callers set the player name/type on `LanguageManager` right before a call.
  - `task/GodUpdateTask` (every 200 ticks, started by `Gods`) gives one god with a believer online its turn and decides when the services act.

  The others: `BelieverService` (gods, prayers, prayer power, chat mode, invitations, priest offers, blessing cooldowns), `HolyLandService` (claims, neutral land, attacks on holy land), `MarriageService`, `GodListService` (`isAllowedGod`, the whitelist's minimum power), `AltarService` (altar blocks and signs, dropped items for sacrifices; no data file), `ChatService` (religion chat and the thread-safe snapshot for the chat thread and PlaceholderAPI), `Permissions` (Bukkit's permission check), `Titles` (screen titles, through `TitleSendEvent`). A service changes the model, then calls `repository.markDirty()` (next autosave) or `repository.save()` (now; holy lands and marriages always did). Rules that need no server are pure static helpers next to them (`GodRules`, `MoodRules`, `RelationRules`, `PriestRules`, `BlessingRules`, `SacrificeRules`, `BelieverRules`, `HolyLandContest`, `AltarSigns`) and are what the tests cover. Keep a service to one area; a new one goes in `GodsContext` (with its repository from `Storage`) and, if it loads a file, in `loadData()`.
- `gods.yml` keeps one section per god name with the keys Gods always wrote (`DivineForce`, `Gender`, `Home.X`, `Priests` as UUID strings, `SacrificeValues.<material>`, …, see `GodRepository`); values it can't read (an unknown god type) and unknown keys are kept. Version 1 (0.9.x and this branch before data versions) is upgraded by `GodsV1ToV2`: `PriestName` and priests kept by name become UUIDs (unknown names are dropped and logged; the `.v1.bak` keeps them) and `LanguageFileName` goes.
- Holy land is stored per 128x128 region and world (`RegionKey`): `Holylands.<world key>.<hash>` / `NeutralLands.<world key>.<hash>`, with `hash = ((long) regionX << 32) | (regionZ & 0xFFFFFFFFL)` and the world key the world name with `.` replaced by `_`. `HolyLandsV1ToV2` drops the 0.9.x `Holyland` / `NeutralLand` sections, whose hash can't be converted.
- To add data: add the field to the model, read and write it in the repository with a new key (keep it a string, number, boolean, list or map), and change it only through the service. Renaming or reshaping existing keys needs a data version: give the file a `VersionedYaml` in `Storage` (or bump its version), add a `Migration` in `migration/` and a test with an old file. A new file gets a `DataFile` and a `Repository` subclass in `Storage`, added to `Storage.files`.

**Settings (`config/`, `migration/`):** `config.yml` is bundled (`plugin/src/main/resources/config.yml`), commented, in kebab-case sections, with a `config-version` (now `2`, `Gods.CONFIG_VERSION`). Gods never rewrites it except to upgrade it or to add missing settings, so admins keep their comments and layout.
- Loading (`Gods.loadSettings`): the bundled file is written on first start; `VersionedYaml` upgrades an older file through the `Migration` chain (keeping `config.yml.v<n>.bak`, writing atomically through `util/AtomicFiles`); `ConfigDefaults.addMissing` adds settings a newer bundled config has (entries of the free-form sections `altars.block-types` and `quests.reward-values` that an admin removed stay removed); then `SettingsLoader` builds `Settings` with the bundled file as defaults.
- `Settings` is an immutable record tree, one record per section (`settings.blessings().blessedSeconds()`), with unmodifiable collections and parsed types (`Material`, `GodType`). `SettingsLoader` validates: a value of the wrong type is logged with its key and gets the bundled default, numbers are clamped, unknown blocks/items/god types are logged and skipped. Nothing pushes settings into managers.
- Code reads settings through `ctx.settings()` (or `Gods#settings()`) every time (never keep a `Settings` or a value from it), so `/g reload` takes effect by swapping that one object.
- `ConfigV1ToV2` upgrades configs from Gods 0.9.x and from this branch before config versions (`Settings.Debug`, `Blessing.MaxBlessingTime`, …): it copies each old key's value into the bundled config (the `MOVED` table, plus the altar, reward and breakable-block lists), and drops obsolete keys (`OBSOLETE`) and warns about unknown ones.
- To add a setting: add the key with its default and a comment to `config.yml` (put the unit in the key name: `-seconds`, `-minutes`, `-hours`, `-days`), add a record component and its read in `SettingsLoader` (with a range check), and read it through `ctx.settings()`. Existing servers get it from `ConfigDefaults` without a version bump. Renaming or moving a key, or changing its meaning, needs `CONFIG_VERSION` + 1 and a new `Migration` (`ConfigV2ToV3`) registered in `Gods.loadSettings`, with a test in `ConfigV1ToV2Test`'s style. `BundledConfigTest` checks the defaults (update `oldDefaults()` when you add one) and that every setting has a comment.

**Quests:** only PILGRIMAGE, SLAY, ITEMSACRIFICE and GIVEITEMS are generated; the other `QUESTTYPE`s stay in the enum because old `quests.yml` files may hold them. Location searches (pilgrimage chests) have a hard cap on attempts and on chunks they load: never loop until a spot is found.

**Managers (`managers/`)** are what is left for phase B4 (`QuestManager`, `HolyBookManager`, `HolyArtifactManager`, `HolyPowerManager`) and the messages phase (`LanguageManager`). `QuestManager` and `HolyBookManager` keep their data in their `DataFile` (see Storage) and still work on the `YamlConfiguration` directly; later phases replace that with models, repositories and services. Players are keyed by **UUID**; never key data by player name. Never write a raw `UUID` (or any other non-primitive object) into a `YamlConfiguration`: SnakeYAML tags it and Bukkit then refuses to load the file. Store `toString()`.
- Holy books and holy artifacts are recognized by `PersistentDataContainer` tags (`gods:holy_book_god`, `gods:holy_power`, …), never by display name or lore; old untagged items are only a fallback.
- Permission checks go through `ctx.permissions().hasPermission`, which is Bukkit's `Player#hasPermission`. There is no Vault dependency.

**Commands (`commands/`):** each subcommand extends `GodsCommand`: the constructor sets `name`, `permission`, `parameters`, `description` and `priestOnly`, and `onCommand(sender, command, args...)` gets `args[0]` = the subcommand name. `/g help` and tab completion are built from the registered commands. To add one:
1. Register it in the `GodsCommandExecuter` constructor (`new CommandX(ctx)`; the command's constructor takes the `GodsContext` and passes it to `super(ctx, "name")`).
2. Declare its permission node in `plugin/src/main/resources/plugin.yml` (and as a child of `gods.*`).

**Language system:** `LanguageManager` uses the `LANGUAGESTRING` enum for keys; messages reach players only through `GodSpeech`. Text comes from `lang/*.yml`:
- `english_general.yml` holds general strings.
- `<lang>_<godtype>_<gender>.yml` holds a god's voice. The file is chosen per god from its type and gender.

The files are bundled in the jar (`plugin/src/main/resources/lang/`) and copied to `plugins/Gods/lang/` when missing. A key missing from a server's copy falls back to the bundled file of the same name, then to the bundled `english_` file with the same suffix (never to another god type). A new god-voice key needs the enum entry plus a line in **all 26** `english_<type>_<gender>.yml` files; a new info key goes under `Info:` in `english_general.yml`.

**Tasks (`tasks/`):** short delayed `Runnable`s (subclasses of `Task`, which takes the context) scheduled through the Bukkit scheduler (divine effects, messages, mob spawns). `task/GodUpdateTask` is the gods' update loop (the target package; phase B4 moves `tasks/` there). Repeating ones must end on their own (a stop time, the player logging off); onDisable cancels whatever is left. A task that runs for the life of the plugin belongs in `Gods` (tracked, see lifecycle).

**Integrations (`integration/`):** `GodsPlaceholderExpansion` (PlaceholderAPI, registered only if that plugin is present, unregistered on disable) and `WorldGuardIntegration` (`ctx.worldGuard()`, null without WorldGuard). Each references the other plugin's classes, so only create it when that plugin is there.

**Listeners (`listener/`)** turn events into service and manager calls, one class per area: `HolyLandListener` (protection, entering land, attacks), `AltarListener` (altar signs, praying/cursing/blessing at altars, sacrifices), `BelieverListener` (a believer's death), `MarriageListener` (wedding tokens), `ChatListener` (religion chat, on the async thread through the `ChatService` cache), `GodListener` (commandments on kills and meals, the online gods list on join/quit), and `QuestAndHolyItemListener`, what is left for phase B4 (quests, holy books, holy artifacts). Both of the last two handle meals and share one `ActionCooldown` (10 seconds, also for reading holy books), which gives every listener the same answer for the same event. Keep the priorities and `ignoreCancelled` flags when moving a handler, and register a switchable one in `startFeatures`.
