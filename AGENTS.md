# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

## Project

Gods is a Bukkit/Spigot plugin. Players build altars, pray to gods they name themselves, and gain powers, quests, holy lands (land protection), marriages, holy books and so on. It runs on Spigot and Paper 1.21.3+ (including 26.x) with Java 21+ (`api-version: '1.21'` in `plugin.yml`). It compiles against `paper-api` 26.3 but **must keep running on Spigot 1.21.3**: use only Bukkit/Spigot API that 1.21.3 has (the `-Pspigot` compile against spigot-api 1.21.3 checks this), and reach Paper-only API behind a runtime check. WorldGuard, PlaceholderAPI, GriefPrevention, Citizens and FancyNpcs are optional (softdepend).

## Build & test

```bash
nix develop                           # devshell with JDK 25 + Maven (flake.nix); or prefix commands with `nix develop -c`
mvn clean package                     # default goal; tests and builds plugin/target/Gods-<version>.jar
mvn test -pl plugin -am -Dtest=SettingsLoaderTest -Dsurefire.failIfNoSpecifiedTests=false  # one test class (append #method for one test)
mvn -Pspigot -pl plugin -am clean compile  # compile against spigot-api instead: fails on any Paper-only API (CI runs this too)
mvn -pl api dependency:build-classpath -Dmdep.outputFile=target/spigot.classpath && java ci/LinkCheck.java plugin/target/Gods-*.jar "$(cat api/target/spigot.classpath)"  # the built jar only references Bukkit API that spigot-api 1.21.3 has (CI runs this too)
```

- A parent `pom.xml` (shared versions and repositories) with two modules, in the standard Maven layout:
  - `api/` (`gods-api`): the public API, `com.dogonfire.gods.api` (see "API"). It is compiled against `spigot-api` 1.21.3 only, with sources and javadoc jars (doclint on: `mvn -pl api javadoc:jar` must pass), and published through JitPack (`jitpack.yml` fetches JDK 25 itself) from release tags as `com.github.DoggyCraft.Gods:gods-api:<tag>`.
  - `plugin/` (`gods`): everything else (`plugin/src/main/java`, `plugin/src/main/resources`, `plugin/src/test/java`). It depends on `gods-api` and bundles it, not relocated. Only `plugin.yml` is Maven-filtered (for `${project.version}`).
- Java 21 bytecode (`maven.compiler.release`), so it runs on 1.21.x servers; it is built with JDK 25 (the flake, CI, JitPack). Don't use Java APIs or language features newer than 21. CI (`.github/workflows/build.yml`) builds on JDK 25 for every push and PR. Pushing a tag `v<pom version>` (e.g. `v1.0.0`) publishes a GitHub release with the plugin and API jars.
- JUnit tests (`plugin/src/test/java`, no server needed) cover config loading and migration, the data file storage, the repositories (each reads a realistic old file from `plugin/src/test/resources/legacy/`, saves it and reads it back unchanged), the data migrations and the message files (`LegacyText`, `LegacyLangFiles`: the old bundled files convert to exactly the new ones and customized ones keep their changes; `MessageKeysTest`; `MessagesTest`), the god themes (`ThemesLoaderTest`: merging, add/remove, names the server lacks, every god type has every list and its effects, every bundled sound exists, the skins per gender and that every bundled skin is a signed texture that decodes), the pure rules of the services (`BelieverRules`, `GodRules`, `MoodRules`, `RelationRules`, `PriestRules`, `BlessingRules`, `SacrificeRules`, `CommandmentRules`, `QuestRules`, `AltarLights`, `HolyPowerRules`, `DevotionRules`, `PowerCooldowns`, `HolyArtifactRules`, `HolyLandContest`, `HolyLandRules`, `DroppedItems`, `AltarSigns`, `AltarClicks`, `AltarClaims`, `AltarScan`, `MainAltarRules`, `HomeRules`, `AltarTexts`, `EffectRules`, `GodNpcRules`, `RankRules`, `NpcProviders`, `SkinTextures`, `ChunkKey`, `ActionCooldown`) the command router and help pages (`CommandRouterTest`, `HelpPagesTest`, `PluginYmlTest`, `PrayForCommandTest`, `GodSkinCommandTest`, `AdminArgsTest`) and the API (`ApiSnapshotsTest`, `GodsApiServiceTest`; `ApiSurfaceTest` in `api/`); test fixtures are in `plugin/src/test/resources`. Most game behavior can only be checked by running the jar on a server.
- `Biome`, `Sound` and other former enums are registry interfaces now: compare with `==`, never `switch` on them or call `valueOf`.

## Architecture

**Entry point and lifecycle:** `com.dogonfire.gods.Gods` (the `JavaPlugin`) only wires things.
- `onEnable` reads `config.yml` into `Settings` (and disables the plugin if it can't, so no data file is overwritten) and the god themes into `Themes` (see "Themes"), creates `Storage` and the `GodsContext`, loads the data in `loadData()` (holy books, marriages, holy land if enabled → messages (after converting old language files) → gods (`GodService`) → altars (`AltarRegistry`) → quests → believers → god white/blacklist), registers the `/g` command (alias `/gods`, `registerCommands()`) and the always-on listeners (`GodListener`, `BelieverListener`, `AltarListener`, `ChatListener`, `AltarWorldListener`, in that order), the PlaceholderAPI expansion, the repeating tasks (the gods' turns `task/GodUpdateTask`, autosave, chat cache refresh, the altar chunk scans `AltarRegistry.processQueue` every tick; kept in `tasks`), and then calls `startFeatures()`. Last it registers `GodsApi` (`service/GodsApiService`) in Bukkit's services manager.
- `startFeatures()`/`stopFeatures()` register and unregister what config.yml switches on and off (now: `QuestListener`, `HolyBookListener` and `HolyArtifactListener` while quests, bibles and holy artifacts are enabled, then `HolyLandListener` and `MarriageListener` while holy land and marriage are; the order matters for handlers of the same event and priority). `stopFeatures()` also undoes what runs on its own: `HolyPowerService.stop()` puts back blocks powers changed, `EffectService.stop()` removes the display entities of running effects, `AltarTextService.stop()` the floating texts above altars (`startFeatures` calls `AltarTextService.start()` always: it removes stray texts, then shows them if `altars.floating-text` is on), `GodNpcService.stop()` the gods' NPCs and lets go of the NPC provider (`startFeatures` registers `GodNpcListener` while `npc.enabled` is on and calls `GodNpcService.start()` always: it removes stray built-in NPCs, picks the provider and shows the NPCs). Put a new switchable listener or repeating task there, through `registerFeature` or a tracked `BukkitTask`, so reload never doubles it.
- `/g reload` (`Gods.reload()`): reads `config.yml` and the themes again (if config.yml fails the old settings and data stay; if themes.yml fails the old themes stay), then `Storage.prepareReload` waits for pending writes and lets each data file decide: one edited on disk since Gods last read or wrote it (or that couldn't be read) is read again, dropping changes not yet saved, so a hand edit wins; every other file keeps what is in memory and is saved. Then `stopFeatures()`, `loadData()` (message files, and the data files: `DataFile.load()` / `Repository.load()` keep the data in memory when `lastLoadKept()`), `startFeatures()`, `Storage.finishReload()`.
- `onDisable` unregisters `GodsApi` and the PlaceholderAPI expansion, stops the features, cancels the tasks (and every delayed task), and `Storage.close()` writes what changed and waits for it.
- New persistent data gets a model, a repository and a service (see "Models, repositories and services"); add the service to `GodsContext` and `loadData()`.

**Object graph (`GodsContext`):** there are no singletons and no static way to reach the plugin. `GodsContext` is built once per enable and owns `Storage`, `Messages` and every service (`ctx.godService()`, `ctx.believerService()`, …, `ctx.plugin()`, `ctx.settings()`, `ctx.themes()`, `ctx.storage()`, `ctx.worldGuard()`, `ctx.griefPrevention()`, `ctx.effectService()`, `ctx.altarRegistry()`, `ctx.altarTexts()`, `ctx.godNpcs()`, `ctx.rankService()`, `ctx.devotionService()`); services, listeners, commands (`SubCommand.ctx`) and tasks (`Task.ctx`) get it through their constructor and keep it in a `ctx` field. The services call each other in cycles, so they keep the context and ask it for the others at use time; a service gets its repository from `Storage` through its constructor. Constructors must not call other services (the graph is still being built). Every service exists even when its feature is off (its data file is then not loaded): check the setting before using a feature's service. A helper that needs the plugin takes it as a parameter (e.g. `new HolyBookItem(plugin, item)`). `ctx.fire(event)` calls one of the API's events and returns it (see "API").

**Storage (`storage/`):** `Storage` owns the data files (`gods.yml`, `believers.yml`, `quests.yml`, `holyland.yml`, `marriages.yml`, `bibles.yml`, `whitelist.yml`, `blacklist.yml`, `altars.yml`), one `DataFile` each held by its `Repository` (`gods()`, `believers()`, `quests()`, `holyLands()`, `marriages()`, `bibles()`, `whitelist()`, `blacklist()`, `altars()`; see below), and the single background thread that writes them. `Storage` also takes a name → UUID lookup (the server's known players), only used to upgrade priests and believers that old `gods.yml` and `believers.yml` files keep by name.
- A service calls its repository's `load()` in its own `load()` and after a change calls `markDirty()` (written by the next autosave, every 3 minutes, on reload and on disable) or `save()` (written now). Never write a data file any other way. A file that was never loaded (its feature is off) is never written.
- A flush takes the YAML text on the main thread and writes it on the storage thread through a temp file (forced to the disk) and an atomic move, so the main thread never waits for the disk and a crash never leaves half a file.
- A file that can't be read is copied to `<file>.broken-<timestamp>`, logged, and is read-only until a later load works: it is never written over. The first load then starts empty, a reload keeps what was in memory. The same goes for a runtime exception from odd YAML in a migration or in a repository's `read()` (the data is used as far as it was read). The old `!!java.util.UUID` tags of `gods.yml` are repaired on load (`Storage.UUID_TAGS`). Each step of `Gods.loadData` is guarded, so one failing file doesn't stop the others.
- A hand edit wins: before each write the writer thread compares the file's modification time with the one Gods last read or wrote; if it differs (edited or deleted), the file is not written (warned once, `DataFile.isEditedOnDisk()`), the changes stay marked, and `/g reload` reads the edit. Disable doesn't write it either.
- `Storage` takes its writer as an `ExecutorService`, so `StorageTest` runs it without a server.
- Every data file but the white/blacklist carries a data version (a `VersionedYaml`, all `data-version: 2` but `holyland.yml`, which is at 3; version 1 is every file from before data versions; `altars.yml`, new in 1.0.0, starts at `data-version: 1`). An older file is copied to `<file>.v<n>.bak` (a second backup of the same version gets a timestamp, so none is ever overwritten), upgraded through its `Migration`s on load and written back at once by its repository; `believers.yml`, `quests.yml`, `marriages.yml` and `bibles.yml` upgrade through `FirstDataVersion` (no change, so their first rewrite has a backup), `gods.yml`, `holyland.yml` (two: `HolyLandsV1ToV2`, `HolyLandsV2ToV3`) and `believers.yml` through their own migration. A new file gets the current version on its first write. `VersionedYaml` checks the whole migration chain before making a backup. A file that can't be upgraded, or whose version is newer than this build knows, is used as it is but never written.
- **Never remove records because another file says so while that file can't be trusted.** Dead gods and priests who stopped praying are judged from `believers.yml`; `Storage.cleanupVerdict()` (`CleanupGuard`, pure and tested) forbids that while `gods.yml`, `believers.yml`, `holyland.yml` or `bibles.yml` is read-only or a load step failed, while there are gods but no believers, and for `CleanupGuard.GRACE_PERIOD` (10 minutes) after a start or reload. Check it before any new cleanup of that kind. Reads (`PriestService.getPriestsForGod`, `isPriest`, command checks, help, tab completion, API snapshots) never change data: maintenance like `PriestService.removeInactivePriests` runs only from `GodUpdateTask`.

**Models, repositories and services** (every domain):
- `model/` holds plain data objects with typed fields (`Instant` for times, `UUID` for players): `God` (with `GodHome`, `ContestedLand`; and the enums `GodType`, `GodGender` (`None` for gods from before genders could be chosen, `Male`, `Female`, `NonBinary`), `GodMood`), `Believer`, `HolyLand`, `NeutralLand`, `ChunkKey`, `Marriage` (one player's proposal, engagement or marriage), `MarriedCouple`, `Quest` (with `QuestLocation`, `QuestTarget` and the enum `QuestType`), `HolyBook`, `Altar` (with `BlockPos`/`BlockPos.ChunkPos` and the enum `AltarKind`), and the enum `HolyPower`. They have no logic and don't save themselves.
- `storage/` has one `Repository` per file (`GodRepository`, `BelieverRepository`, `HolyLandRepository`, `MarriageRepository`, `QuestRepository`, `HolyBookRepository` for bibles.yml, `GodListRepository` for whitelist.yml and blacklist.yml, `AltarRepository` for altars.yml). `load()` reads the `DataFile`'s YAML into models; after that the models are the truth, and each flush asks the repository for a fresh YAML snapshot (`write`) on the main thread. The files keep the keys and the time formats they always had (`util/LegacyDates`: `"HH:mm:ss dd-MM-yyyy"`, holy land and quests `"HH:mm dd-MM-yyyy"`, server time zone): a time that can't be parsed reads as never but is kept as it was (in the extras, `Repository.readTime`) and written back until a new time replaces it. Keys a repository doesn't know are written back unchanged: top-level ones (e.g. entries keyed by player name in very old files) through `keepUnknown`, those inside an entry through the model's `extras`.
- `service/` owns every change. The gods (all on `GodRepository`, one `gods.yml`):
  - `GodService`: creating and removing gods, which gods exist and have a believer online, type/gender/color/title/voices, gender changes (`changeGender`, for `/g gender` and `GodsApi.setGender`: fires `GodGenderChangeEvent`, stores `GenderChangedTime`, the god tells its believers; the caller checks the cooldown, `GodRules.genderChangeWait`), seed and verbosity, power (from the believers), description, the religion's home (`getHome`, see "Altars"), the main altar's sign (`getMainAltar`/`setMainAltar`), access, holy land PvP/mob settings, last quest time; it loads `gods.yml`.
  - `MoodService`: mood, pleased/angry modifiers, falloff. `RelationService`: alliances and wars, and the attacker's side of an attack on holy land (`HolyLandService` owns the land's side).
  - `PriestService`: priests (left out of reads when they stop praying, removed by the update loop), priest offers and answers, assign/remove with the configured console commands, reminders. `BlessingService`: blessings and curses on players (effects, items, healing, holy artifacts, lightning, mobs) and a god's blessed/cursed player. `CommandmentService`: holy/unholy food and mobs (each picked once from the god type's theme and kept), eating and killing, sacrifices and sacrifice needs (`CommandmentRules`: picks that never loop, whatever themes.yml says). `PrayerService`: praying at altars (creating the god), joining/changing god, `/g yes`/`/g no`, leaving, dying, lost believers (`removeLostBelievers`, see "Prayer power decay").
  - `GodSpeech`: a god's words (`say`, `sayToBelievers`, …, `GodSpeakTask`) and the delayed info messages (`sendInfo`, `InfoTask`); see "Messages".
  - `task/GodUpdateTask` (every 200 ticks, started by `Gods`) gives one god with a believer online its turn and decides when the services act.

  Quests, holy books, holy artifacts and powers:
  - `QuestService` (on `QuestRepository`, `quests.yml`, loaded always): making a new quest, counting progress when believers act (`handleKilledMob`, `handleSacrifice`, `handleReadBible`, `handleOpenChest`, …), completing and failing quests, rewards, and the quest speech table (`Phase` → `Voice` per `QuestType`). `QuestRules` has the numbers (sizes, durations, targets, expiry, reward rolls, holy names, pilgrimage spots), drawn from the `Random` in the order the old code drew them; `PilgrimageSites` finds, places and removes pilgrimage chests.
  - `HolyBookService` (on `HolyBookRepository`, `bibles.yml`, loaded while bibles are enabled): each god's book (a default one written from its commandments when first needed), copies, editable copies, `/g setbible`, and which god a book belongs to. `HolyBookItem` wraps the book item.
  - `HolyArtifactService` (no data file; the state is in the item's tags): making an artifact for a god type (as strong as the giving god's rank at that moment, `HolyPowerRules.strength`: 1 for spirits and recognized gods, 2 descended, 3 exalted, 4 greater; FIREBALL and ICE always 1; kept in `gods:holy_power_value`, so existing artifacts keep theirs; the lore line `artifact.power.<POWER>` shows `<value>`/`<double>` and the effect's real `<radius>`, `<distance>`, `<hearts>`), recognizing one, using one (uses, rank, wear). `HolyArtifactRules`: rank names and lore lines.
  - `HolyPowerService`: cooldowns (`PowerCooldowns`, per player and power, and one sky power per world at a time) and starting a power; the powers are in `service/power/` by kind (`SkyPowers`, `GiftPowers`, `NaturePowers`, `AttackPowers`). `HolyPowerRules`: each power's lore text (`describe`) and reading it back from old artifacts (`parse`), cooldowns, effect radius, the safe spot TELEPORT and /g home may land on (`isSafeSpot`, on the world's blocks through `util/SafeSpots`), EARTHQUAKE damage. Powers must not grief or kill: no real explosions or lightning (`util/Lightning`: `strikeLightningEffect` plus lightning damage from that bolt, so holy and neutral land protect as against lightning), teleports only to safe spots in loaded chunks as `ENDER_PEARL` teleports (so holy land checks them), blocks a power changes for a while are tracked and put back (ICE: packed ice that can't be broken; `HolyPowerService.stop()` puts everything back when the plugin stops), TAME only untamed animals.

  The others: `BelieverService` (gods, prayers, prayer power and its decay (`decayPrayerPower`), chat mode, invitations and who sent them, priest offers, blessing cooldowns), `DevotionService` (believers' devotion, on `BelieverRepository`, see "Devotion"), `HolyLandService` (holy land, neutral land, attacks on holy land, see "Holy land"; `HolyLandRules.isWorldSpawn`: holy and neutral land only stop mobs the world spawns, never eggs, breeding, commands or plugins), `MarriageService`, `GodListService` (`isAllowedGod`, the whitelist's minimum power), `AltarService` (altar blocks and signs, see "Altars"; dropped items for sacrifices (`DroppedItems`: an item counts once, when it first catches fire in fire or lava, and is forgotten when it despawns); no data file), `AltarRegistry` (on `AltarRepository`, `altars.yml`: where the altars are, and main altars), `AltarTextService` (the text floating above altars), `ChatService` (religion chat and the thread-safe snapshot for the chat thread and PlaceholderAPI), `Permissions` (Bukkit's permission check), `Titles` (screen titles, through `TitleSendEvent`; the texts come rendered by `Messages` and are shown as they are), `EffectService` (themed effects, see "Effects"), `RankService` (ranks and lifetime stats, on `GodRepository`, see "Ranks"). A service changes the model, then calls `repository.markDirty()` (next autosave) or `repository.save()` (now; holy lands and marriages always did). Rules that need no server are pure static helpers next to them (`GodRules`, `MoodRules`, `RelationRules`, `PriestRules`, `BlessingRules`, `SacrificeRules`, `BelieverRules`, `QuestRules`, `HolyPowerRules`, `HolyArtifactRules`, `HolyLandContest`, `AltarSigns`) and are what the tests cover. Keep a service to one area; a new one goes in `GodsContext` (with its repository from `Storage`) and, if it loads a file, in `loadData()`.
- `gods.yml` keeps one section per god name with the keys Gods always wrote (`DivineForce`, `Gender` (`None`, `Male`, `Female`, `NonBinary`), `GenderChangedTime`, `Home.World/X/Y/Z` (the home from before main altars: read and kept, never written for new gods), `MainAltar.World/X/Y/Z` (the main altar's sign), `NpcSkin.Name/Value/Signature` (/g godskin), `PriestSince`, `DescendedTime`, `AscendingSince` (since when it has had too few believers for its rank), `Rank`, `RankSince`, `Stats.Prayers/Sacrifices/Quests/Converts`, `StatsSeeded` (see "Ranks"), `Priests` as UUID strings, `SacrificeValues.<material>`, …, see `GodRepository`); values it can't read (an unknown god type) and unknown keys are kept. Version 1 (0.9.x and this branch before data versions) is upgraded by `GodsV1ToV2`: `PriestName` and priests kept by name become UUIDs (unknown names are kept under `UnresolvedPriests` and logged) and `LanguageFileName` goes. `believers.yml` version 1 is upgraded by `BelieversV1ToV2`: entries keyed by player name move to the UUID (unknown names, or players who already have a UUID entry, go under `Unresolved.<name>`). `believers.yml` also keeps each believer's devotion (`Devotion` (missing: a believer from before devotion, seeded once), `DevotionLevel` (missing: follower), `DevotionSince`, `DevotionFaded`) and who sent their invitation (`Invitation.By`), and up to when the decay of their prayer power was counted (`PrayerPowerDecayed`, see "Prayer power decay"); new keys, no data version.
- Holy land is stored per chunk (`ChunkKey`: world key and chunk x/z, the world key the world name with `.` replaced by `_`), one `HolyLand` per altar (see "Holy land"): `Holylands.<world key>."cx,cz"` (the land's id, its center chunk when it was made) with `GodName`, `Name`, `World` (the real name), `Center: "cx,cz"` (the altar block's chunk), `Chunks: ["cx,cz", ...]`, `FirstPrayerTime`, `LastPrayerTime` and the attack keys (`AttackingGodName`, `ContestedTime`, `AttackerKills`, `DefenderKills`, `Desecration`), and `NeutralLands.<world key>."cx,cz": <time set>`. The ids are `"cx,cz"`, never `cx_cz` (YAML 1.1 reads `3_4` as the number 34). `HolyLandRepository` indexes every chunk to its land, so lookups by location are hash hits; a chunk two lands list (a hand edit) belongs to the first. `HolyLandsV1ToV2` drops the 0.9.x `Holyland` / `NeutralLand` sections, whose hash can't be converted; `HolyLandsV2ToV3` turns version 2's 128x128 regions (`<hash>` = region X in the high 32 bits, Z in the low) into chunks: each region land becomes one land of its 64 chunks centered on its middle chunk (rx*8+4, rz*8+4), each neutral region its 64 neutral chunks. gods.yml's `ContestedLand` keeps the block an attack started at (the land is the one at that block); its `Hash` is only read and written back while an attack from before chunks lasts (`ContestedLand.hash`, null for newer ones).
- `quests.yml` (the keys never changed) keeps one section per god (`Type` as `"Pilgrimage"`, `Amount`, `TargetType`, `MaxDuration`, `Progress`, `Players` as UUID strings, `Contributors` (the believers whose deeds counted, for devotion), `CreatedTime`, `Location.World/X/Y/Z/Ground`) and `QuestTargets.<hash>` (`God`, `Location`), with the hash `x * 73856093 ^ y * 19349663 ^ z * 83492791` (`QuestTarget.keyFor`). A missing `Amount`/`Progress`/`Players` stays missing. Loading drops what 0.9.x left that can't be used (the `Global` section, HOLYWAR/SLAYDRAGON/GETHOLYARTIFACT/PVPREVENGE quests and their targets) and writes the file back (after the `.v1.bak` backup). `bibles.yml` keeps `<god>.Title`, `.Author`, `.Pages`.
- To add data: add the field to the model, read and write it in the repository with a new key (keep it a string, number, boolean, list or map), and change it only through the service. Renaming or reshaping existing keys needs a data version: give the file a `VersionedYaml` in `Storage` (or bump its version), add a `Migration` in `migration/` and a test with an old file. A new file gets a `DataFile` and a `Repository` subclass in `Storage`, added to `Storage.files`.

**Settings (`config/`, `migration/`):** `config.yml` is bundled (`plugin/src/main/resources/config.yml`), commented, in kebab-case sections, with a `config-version` (now `7`, `Gods.CONFIG_VERSION`). Gods never rewrites it except to upgrade it or to add missing settings, so admins keep their comments and layout.
- Loading (`Gods.loadSettings`): the bundled file is written on first start; `VersionedYaml` upgrades an older file through the `Migration` chain (keeping `config.yml.v<n>.bak`, writing atomically through `util/AtomicFiles`); a file without `config-version` that already has the kebab-case sections (`ConfigV1ToV2.isVersion2Layout`) is taken as version 2 and only gets the key, never "upgraded" (which would reset it); a file from a newer Gods is used as it is and never written (no missing settings added); `ConfigDefaults.addMissing` adds settings a newer bundled config has (entries of the free-form sections `altars.block-types` and `quests.reward-values` that an admin removed stay removed); then `SettingsLoader` builds `Settings` with the bundled file as defaults.
- `Settings` is an immutable record tree, one record per section (`settings.blessings().blessedSeconds()`), with unmodifiable collections and parsed types (`Material`, `GodType`). `SettingsLoader` validates: a value of the wrong type is logged with its key and gets the bundled default, numbers are clamped, unknown blocks/items/god types are logged and skipped. Nothing pushes settings into services.
- Code reads settings through `ctx.settings()` (or `Gods#settings()`) every time (never keep a `Settings` or a value from it), so `/g reload` takes effect by swapping that one object.
- `ConfigV1ToV2` upgrades configs from Gods 0.9.x and from this branch before config versions (`Settings.Debug`, `Blessing.MaxBlessingTime`, …): it copies each old key's value into the bundled config (the `MOVED` table, plus the altar, reward and breakable-block lists), and drops obsolete keys (`OBSOLETE`) and warns about unknown ones.
- `ConfigV2ToV3` moved altar blocks into the themes: it removes the `altars.block-types` lists that are still Gods' old defaults (so those god types get their theme's blocks), keeps the admin's own, and gives god types a config left out an empty list (they had no altar blocks).
- `ConfigV3ToV4` removed `priests.only-priests-can-set-home` (the home became the main altar, which only priests choose); `ConfigV1ToV2` lists the 0.9.x key as obsolete.
- `ConfigV4ToV5` made the descent the descended rank: it adds the bundled `ranks` section (with its comments) and moves `npc.descend.requires-priest`, `min-believers`, `hours-after-priest` and `min-power` to `ranks.descended.*` and `ascend-grace-hours` to `ranks.drop-grace-hours`. `ranks.recognized`/`descended`/`exalted`/`greater` are free-form sections (`ConfigDefaults.FREE_FORM_SECTIONS`): a condition an admin removed is not added back, and `SettingsLoader` reads a rank section without the bundled defaults (only a missing section is the bundled one).
- `ConfigV5ToV6` replaced `believers.max-hours-without-prayer` by the prayer power decay (see "Prayer power decay"): it removes the key and sets `believers.decay-after-days` to `ConfigV5ToV6.decayAfterDays` (hours / 48, rounded, at least 1: half the old patience is the quiet period, the decay about the rest; a `decay-after-days` already there wins), with the bundled comment; the other new keys come from `ConfigDefaults`. `ConfigV1ToV2` maps 0.9.x's `Settings.MaxBelieverPrayerTime` the same way (its bundled config is already version 6). `priests.max-hours-without-prayer` stays.
- `ConfigV6ToV7` replaced the extra holy land regions per rank by the land's reach: it removes `ranks.unlocks.holy-land-extra-regions` and adds `ranks.unlocks.holy-land-radius-chunks` from the bundled config with its comment (a radius already there is kept).
- To add a setting: add the key with its default and a comment to `config.yml` (put the unit in the key name: `-seconds`, `-minutes`, `-hours`, `-days`), add a record component and its read in `SettingsLoader` (with a range check), and read it through `ctx.settings()`. Existing servers get it from `ConfigDefaults` without a version bump. Renaming or moving a key, or changing its meaning, needs `CONFIG_VERSION` + 1 and a new `Migration` (`ConfigV7ToV8`) registered in `Gods.loadSettings` (and in the tests' migration lists), with a test in `ConfigV1ToV2Test`'s style. `BundledConfigTest` checks the defaults (update `oldDefaults()` when you add one) and that every setting has a comment.

**Themes (`config/Theme`, `Themes`, `ThemesLoader`):** what each god type is about lives in data, not code. `plugin/src/main/resources/themes.yml` (in the jar, never written to disk) has a section per god type (lower case) and a `default` section (the theme of gods without a type, and what fills a key a type leaves out), each with `holy-mobs`, `unholy-mobs`, `holy-foods`, `unholy-foods`, `sacrifice-needs`, `slay-targets`, `curse-mobs`, `peaceful-mobs`, `altar-blocks` and `sign` (`messages`: the `altar.sign.<messages>` texts, `dye`, `glowing`), `ranks` (a name per rank, `spirit` to `greater`; merged per key like `sign`, see "Ranks") and `effects` (`symbol`, and `pleased`/`neutral`/`angry` each with `particles`, `sounds` (sound ids, kept as `minecraft:` keys; on a server checked against `Registry.SOUNDS`) and `colors` (dye colors or `#RRGGBB`); merged per list like the rest, see "Effects"), and optionally `npc` (`skin` with `god`, `goddess` and/or `deity`, each the `value`/`signature` of a texture Mojang signed; no player names, no texture without a gender: those, a missing signature and a value that isn't a texture are warned about with a hint (mineskin.org or `/g godskin`) and ignored; the admin's file replaces each gender entry it lists, `''` removes one, `skin: ''` all; a type's skins don't take the default section's, that fallback is `GodNpcRules.skin`'s; no `add:`/`remove:`; `ThemesLoader.readNpc`, `Theme.npcSkins()`, see "God NPCs"). `plugins/Gods/themes.yml` only holds the admin's changes: Gods writes it once from `themes-overrides.yml` (all comments) and never again, so the themes need no migrations. `ThemesLoader.merge` merges it key by key: a list replaces Gods' list, a section with `add:`/`remove:` changes it. Names are resolved at runtime (`ThemesLoader.Names`), so the bundled file may name mobs, foods and blocks newer than Spigot 1.21.3 (happy ghast, copper golem, nautilus, …): a name the server lacks is skipped with a debug message when the bundled file has it or `version-names.txt` lists it (the Material and EntityType names that differ between spigot-api 1.21.3 and 26.3, generated by comparing the two APIs' constants; add newer versions' names the same way), and warned about otherwise (a typo). Never reference such a constant in code. The result is an immutable `Themes` read through `ctx.themes()` every time, like the settings; `ThemesLoaderTest` checks that every bundled name exists in the newest API and every god type has every list.
- Gods pick from their type's theme (`CommandmentService.themeForGod`; an empty list falls back to the default theme's): holy/unholy mob and food once (a stored one is kept, even one the theme no longer has), sacrifice needs (the seed picks five, plus the unholy food) and slay quest targets (`QuestRules.slayTarget`: half the draws from the list, half the unholy mob, as before with five targets). A curse's mobs (`BlessingService.strikePlayerWithMobs`) are one kind drawn from `curse-mobs` (`BlessingRules.curseMob`; empty: the default theme's; `SpawnHostileMobsTask` provokes wolves, bees and zombified piglins); in the holy land of a god that doesn't allow mob spawning the world may spawn only its holy mob and its theme's `peaceful-mobs` (`HolyLandService.isMobTypeAllowedToSpawn`; taken as it is, so `[]` means none; a nature god's land lets everything spawn, as before). The default theme's lists are the ones Gods had built in (`ThemesLoaderTest`).
- To change what a god type is about, edit `themes.yml` (keep lists non-empty; add every new mob and item to `names.mob.*`/`names.item.*` in messages.yml, which `MessageKeysTest` checks).

**Altars (`AltarService`, `AltarSigns`, `AltarLights`, `AltarRegistry`, `AltarTextService`, `listener/AltarListener`, `listener/AltarWorldListener`):** an altar is an altar block, a light on top and a wall sign on its side (front only; no hanging signs).
- Altar blocks: `ctx.themes().altars()` (`Themes.combineAltars`): for a god type that config.yml's `altars.block-types` lists, that list as it is (an empty list: no altar makes the type); for the others the theme's `altar-blocks`. The bundled config lists none. A block of several god types makes one at random; the bundled themes have no block twice (tested), and thunder lists every copper oxidation and waxed variant so an altar keeps working as it ages.
- Lights (`AltarLights`): torches, soul and redstone torches, lanterns, soul lanterns, candles of any color (lit or not) and candle cakes (through `Tag.CANDLES`/`CANDLE_CAKES`), and copper torches and lanterns by name where the server has them. The light doesn't decide anything else.
- A new praying altar sign has the god's name on one line and maybe a gender word on another (`AltarSigns.newPrayingAltar`; `AltarSigns.GenderWords` from `altar.gender-words.male/female/non-binary` plus English "God"/"Goddess"/"Deity", `AltarService.genderWords()`, which `/g gender` reads too); a sign with only the name works as always, even if the name is a gender word. Two lines are only taken as an altar when one is a gender word. Without a word, a new god takes `GodRules.chosenGender(seed)` (male, female or non-binary; the seed is made before the god, `GodService.newSeed`) and says `believer-god-chose-gender` (`<gender>` names it). Existing gods keep their gender; gods with `None` keep the voice their seed gives them (`seed & 1`, as before). Praying sign texts know `<gender>` and `<title>`, so after `/g gender` a sign that shows them is rewritten when next used (no world scan).
- Every finished altar sign is tagged in its `PersistentDataContainer`: `gods:altar` (`praying`, `curses`, `blessings`), `gods:altar_god` (a praying altar's god; on a curse/blessing sign the builder's god, for the style), `gods:altar_player` (UUID string) and `gods:altar_player_name`. `AltarService.readAltarSign` recognizes a sign by its tags first, then by the text altars had before tags (`AltarSigns.recognize`); `refreshAltarSign` tags such an old sign on first use and rewrites any sign whose text, dye or glow isn't its god type's style (`altar.sign.<style>.<kind>` from messages.yml as legacy lines on `Side.FRONT`, the theme's dye and glowing text), then waxes it. New signs get their text through the `SignChangeEvent` and their tags, style and wax a tick later (`finishAltarSignLater`).

- Praying at the whole altar (`AltarClicks`, `AltarService.altarPart`/`findPrayingSign`): a right click on the altar block or its light prays through the same code as a click on the sign (`AltarListener.useAltarSign`), with the praying sign hanging on the altar block (facing away from it; a tagged one first, never a curse or blessing sign). Vanilla keeps the click (`AltarClicks.praysOnClick`): off hand, sneaking, a block with its own use (`Material.isInteractable()`; for lights, candle cakes), and items that work on blocks (flint and steel, fire charges, axes, shovels, hoes, buckets, honeycomb, shears, bone meal, spawn eggs, more of the clicked block). Both hands' events are decided by the main hand's item, so the off hand doesn't act after a prayer; clicks that don't pray are left untouched, and one another plugin denied doesn't pray.
- Claims (`AltarClaims`, `integration/GriefPreventionIntegration`): with `altars.require-claim` on and GriefPrevention installed, a new altar sign (any kind) and its altar block must be in a claim where the builder has build trust (`Claim.checkPermission(player, ClaimPermission.Build, null) == null`), or in a world where GriefPrevention has claims off; otherwise `altar.not-in-claim` and the sign is dropped like other refused altars. Only new altars are checked (in `AltarListener.onSignChange`, before `handleNew*`); existing ones keep working.
- Registry (`service/AltarRegistry`, `storage/AltarRepository`, `altars.yml`, `listener/AltarWorldListener`): Gods knows where its altars are. An `Altar` is its wall sign (which identifies it; an altar block can carry several), the block it hangs on, its `AltarKind` and god (a curse/blessing sign's is the builder's god), and when and by whom it was built (both null for altars found or used rather than built under Gods' eyes). `altars.yml` is a list (`World`, `Sign`/`Block` as `"x,y,z"`, `Kind`, `God`, `Created`, `Creator`; world names are values because they may hold dots), indexed in memory by sign, altar block and chunk (the sign's and the block's), so event and chunk lookups are hash hits. The world is the truth and the file is its memory:
  - Added when a sign is finished as a new altar (`AltarService.finishAltarSignLater`, with the builder), when an altar is used (`AltarListener.useAltarSign`, after `refreshAltarSign` tagged it) and when a scan finds a tagged sign.
  - Scans: `ChunkLoadEvent` (not new chunks) and, on enable and `/g reload`, every loaded chunk of an active world are queued; `processQueue` (every tick) scans at most `AltarScan.CHUNKS_PER_TICK` still-loaded chunks, each through `Chunk.getTileEntities()` only (wall signs with the `gods:altar` tag, read by `AltarService.readTaggedAltar`). `AltarScan.reconcile` (pure) adds what the registry lacks, updates what differs and removes registered altars whose sign is no longer a tagged sign. Never scan block by block or load chunks for it.
  - Removed: block events that touch a sign or altar block (break, burn, entity/block explosion, piston extend/retract, `EntityChangeBlockEvent`, place; MONITOR, `ignoreCancelled`) queue the sign for a check a tick later (`blocksChanging`), which removes it only if the sign is gone or untagged then (breaking the altar block drops the sign). A removed praying altar (or one whose sign changes god or kind) takes its holy land with it when no other praying altar of its god stands in that land (`HolyLandService.altarRemoved`, see "Holy land"). Removing an altar depends on the world only, never on another data file, so `CleanupGuard` doesn't apply.
  - A removed god's altars stay registered (they still stand; praying at one founds the god anew); they have no floating text while the god doesn't exist.
- Main altar (`AltarRegistry`, `MainAltarRules`, `/g setaltar` alias `/g sethome`, `SetAltarCommand`): every god has one while it has a registered praying altar. It is stored on the god (`God.mainAltar`, `MainAltar.*` in gods.yml, the sign's block; `GodService.getMainAltar`/`setMainAltar`), not in altars.yml; `AltarRegistry.isMainAltar` compares.
  - Automatic: the altar a god is founded at (`GodService.createGod` takes its sign; even when older altars of a removed god of that name stand). A god without one (from before main altars, or whose main altar is gone) gets `MainAltarRules.automatic` (pure, tested) of its registered praying altars: the oldest by `Created` among those that know it, else the first the registry found. `AltarRegistry.chooseMainAltar` runs on `load()` for every god and whenever an altar is registered or changes (`apply`). A stored main altar is never replaced while it is set, even when the registry hasn't found it again yet (altars.yml lost).
  - When the main altar is removed, its sign changes god or kind, or a new sign is gone before it was finished (`notBuilt`), `dropMainAltar` clears it and picks the oldest remaining one; the priests hear `priests-main-altar-moved` (`<world>`, `<x>`, `<y>`, `<z>`: its altar block) or, with no altar left, `priests-main-altar-lost`.
  - `/g setaltar`: a priest makes a registered praying altar of their god the main altar by looking at its sign, altar block or light (`getTargetBlockExact(MainAltarRules.REACH_BLOCKS)`; `MainAltarRules.candidates`/`choose`, pure); the believers hear `believers-set-home`. Every change goes through `AltarRegistry.setMainAltar` (floating texts) and `GodService.setMainAltar` (saved now, the NPC follows).
  - `/g info` shows it to the god's believers (and the console) and tells priests when there is none; `GodInfo.mainAltar()` is its altar block. `AltarRegistry.mainAltar`/`mainAltarLocation` and `MainAltarRules.standingSpot` (the block in front of the sign) are where the god's NPC stands (see "God NPCs").
- Home (`/g home`, `HomeCommand`, `HomeRules`, pure, tested): the religion's home is the main altar's standing spot, facing the altar (`HomeRules.home`, `GodService.getHome`); a god without a main altar keeps the `Home` gods.yml has from before (`GodHome`; never written any more), else it has none. `/g home` lands on the spot if `util/SafeSpots.isSafe` (solid ground that doesn't hurt, two free blocks, no liquid or fire, not the void), else on the nearest safe spot within `HomeRules.SEARCH_RADIUS_BLOCKS` (`HomeRules.safeLanding`; never the altar's sign, block or the two blocks above it), else `command.home.unsafe`. `GodInfo.home()` is the same home (`ApiSnapshots.home`).
- Floating text (`service/AltarTextService`, `AltarTexts`): with `altars.floating-text` `all` (default) or `main`, a `TextDisplay` floats `AltarTexts.HEIGHT` above the altar block of each registered praying altar of an existing god (only main altars with `main`): `altar.floating.<style>.altar` or `.main` from messages.yml (the theme's sign style, else `default`; `<god>`, `<title>`, `<gender>`, `<mood>`, `<believers>`, `<rank>`; blank lines are dropped), billboard center, view range from `altars.floating-text-view-distance-blocks`. Rules: spawned through `World.spawn(…, setup)` with `setPersistent(false)` and the `gods:floating` PDC tag before it enters the world; only while both the sign's and the block's chunks are loaded (shown after a scan, hidden on `ChunkUnloadEvent`), at most `AltarTexts.MAX_DISPLAYS`, tracked by sign and removed when the altar goes and by `stop()`; `start()` first removes tagged displays it doesn't track (strays). Texts change lazily (`refreshGod`: the god's turn in `GodUpdateTask`, `changeGender`, `createGod`/`removeGod`, a new main altar), and only when the text differs; never refresh every tick.

**God NPCs (`service/GodNpcService`, `GodNpcRules`, `integration/npc/`, `listener/GodNpcListener`, `command/GodSkinCommand`):** a god that has descended stands as an NPC on `MainAltarRules.standingSpot` of its main altar, facing the altar (`GodNpcRules.facingYaw`), and a right click on it prays exactly like a click on the altar's sign (`PrayerService.prayAtAltarSign`, which `AltarListener` uses too: same permission, name, access, cooldown, effects and `BelieverPrayEvent`).
- Providers (`GodNpcProvider`: `show(NpcSpec)`, `remove`, `close`, `godOf(entity)`, `entity(god)`, `tick`): `NpcProviders.choose` (pure, tested) turns `npc.enabled`/`npc.provider` into one: `auto` is Citizens if enabled, else FancyNpcs if enabled, else the built-in mannequin where the server has one, else none; a named provider the server lacks gives none with a warning. `GodNpcService.start()` (from `startFeatures`) makes it, `stop()` closes it. Each provider makes NPCs that are never saved and owns their lifecycle; `NpcSpec` (location with yaw, name or null, `NpcSkin` or null) is what the NPC should be, and `show` does nothing when it already is (`NpcSpec.sameAs`); a changed skin makes a new NPC.
  - `MannequinNpcs` (built-in): the vanilla mannequin (1.21.9+). Gods supports 1.21.3, which has none, and Spigot's and Paper's `Mannequin` differ (Spigot `setPlayerProfile(PlayerProfile)`, `setDescription(String)`, `setHideDescription`; Paper `setProfile(ResolvableProfile)`, `setDescription(Component)`), so nothing names `Mannequin` or `EntityType.MANNEQUIN`: the type comes from `Registry.ENTITY_TYPE` by key, is spawned through its entity class with `World.spawn(…, setup)`, and its own methods are found by reflection once (`Calls`), Paper's path when the interface has `setProfile`. Paper gets a `ResolvableProfile` built with the signed `textures` property; Spigot a `PlayerProfile` with the skin URL and model (`SkinTextures.decode`). Paper's description is hidden with `setDescription(null)` (the server's own Component type; Gods' relocated Adventure is never passed). Any failure is logged once and no more mannequins are made. Each one is `setPersistent(false)`, tagged `gods:npc` (its god) before it enters the world, invulnerable, immovable, silent, without gravity or AI; `start()` removes tagged strays, also when another provider is used. Once a second (`tick`) it turns toward the nearest player within `GodNpcRules.LOOK_RADIUS_BLOCKS`, else back to the altar, only when off by more than a few degrees.
  - `CitizensNpcs`: PLAYER NPCs in Gods' own in-memory registry (`CitizensAPI.createInMemoryNPCRegistry("Gods")`, removed on close), protected, silent, not collidable, `LookClose` trait; `SkinTrait`: a signed texture with `setSkinPersistent`, else the name with `setSkinName`; `setFetchDefaultSkin(false)` so an NPC never wears the skin of a player who happens to have the god's name. Compiled against `net.citizensnpcs:citizens-main` (provided, `maven.citizensnpcs.co`, snapshots only).
  - `FancyNpcsNpcs` (Paper only): packet NPCs, `setSaveToFile(false)`, turn-to-player, not in tab; only signed textures are passed (a name would make FancyNpcs look it up); the display name is FancyNpcs' MiniMessage, so the god's name goes in escaped as a string (`<empty>` for none). No server-side entity: clicks come through its `NpcInteractEvent` (moved to the main thread if needed), `godOf`/`entity` know none. Waits for `NpcManager.isLoaded()` (`ready()`). Compiled against `de.oliver:FancyNpcs` 2.9.2, the newest whose API jar is Java 17 bytecode (2.10+ is Java 25, which the Java 21 compile can't read); the API Gods uses is the same in 2.11.
  - Citizens' and FancyNpcs' classes are only touched in their provider, which is only made when that plugin is enabled (like WorldGuard). The `-Pspigot` compile and the link check stay green because neither the mannequin nor Paper types are named anywhere.
- When (`GodNpcService.specFor`): only for an existing god that has descended, whose main altar is registered as its praying altar, in an active world, with the chunks of its sign, altar block and spot loaded and a figure fitting on the spot (`GodNpcRules.fits`: feet and head passable); at most `GodNpcRules.MAX_NPCS`. Shown or updated when a chunk with the altar is scanned (`AltarRegistry.scan` → `chunkScanned`), the main altar changes (`GodService.setMainAltar`), the god is created or removed, and on the god's turn (`GodUpdateTask`); removed when a chunk of altar or spot unloads (`chunkUnloading`) and by `stop()`. The name shows above it only with `altars.floating-text: off` (`GodNpcRules.showsName`): the floating text already shows it. `GodNpcListener` (registered while `npc.enabled`) cancels clicks and damage on NPCs with an entity; only the main hand's click prays (`GodNpcRules.click`), and one another plugin cancelled doesn't.
- Descent: a god has descended while its rank is `DESCENDED` or higher (see "Ranks"); `DescendedTime` follows the rank (`RankService.setRank`). Rising into it (`RankService.change`) fires `GodDescendEvent` (cancellable: try again later) after `GodRankChangeEvent`, then saves, and `GodNpcService.descended` shows the NPC with `World.strikeLightningEffect` (no damage) and `EffectService.descent`, also without an NPC provider; the god says `believers-god-descended`. Falling below it removes the NPC, fires `GodAscendEvent` (not cancellable) and the god says `believers-god-ascended`. Losing the main altar doesn't make it ascend.
- Skins: `GodNpcRules.skin`, the first there is of: the god's own (`/g godskin`, `NpcSkin` in gods.yml); for a god (Male, and None: gods from before genders) its theme's `god`, the default section's `god`; for a goddess (Female) its theme's `goddess`, the default section's `goddess`; for a deity (NonBinary) its theme's `deity`, its theme's `god`, the default section's `deity`, the default section's `god` (never a goddess's, no random pick); else none (the plain look, only when an admin removed the default section's skins). `GodService.changeGender` refreshes the NPC, so it changes skin with the gender. Themes hold only signed textures; a god's own skin known only by name (a hand edit of gods.yml) is resolved by `SkinResolver` (an online player's profile at once, by reflection because Paper's `getPlayerProfile()` returns its own type; anyone else's through `PlayerProfile.update()` off the main thread, answered on the main thread, kept for the plugin's life; failures aren't retried for 10 minutes); until then the NPC gets the name (Citizens fetches it, the mannequin and FancyNpcs show the default look) and the NPCs are refreshed when it is known. Paper gives the signed `textures` property; Spigot only the URL and model, kept as an unsigned value (`SkinTextures.encode`), which the mannequin takes but player NPCs don't (they get the name). `/g godskin <player>` (priest-only, `gods.priest.godskin`, `command.disabled.npc` while `npc.enabled` is off) resolves the skin (an online player's current one, even if an older one is cached) and stores name, value and signature on the god; `/g godskin` alone does the same with the priest's own name (`GodSkinCommand.skinOf`); `/g godskin reset` clears it. Never invent textures: bundled ones must be real signed textures, each with a comment saying where it comes from (MineSkin links; the werewolves' goddess is the WerewolfAlpha texture from DoggyCraft's Werewolf plugin). Bundled now: the default section's god, goddess and deity (so a deity of a type without its own deity or god skin wears the default deity), a god and a goddess for every type but party (thunder's Zeus and a storm goddess, sun's god and Amaterasu, wisdom's god and Athena, evil's the same texture for both, werewolves' goddess the WerewolfAlpha), party's god (Dionysus, so its goddesses wear the default goddess) and moon's deity (the only type deity: other types' deities wear their type's god skin).

**Effects (`service/EffectService`, `EffectRules`):** short themed effects at prayers (`PrayerService.handleAltarPray`, the god's mood; with prayer effects off there is none, not even the flame puff of old), sacrifices (`CommandmentService.handleSacrifice` by verdict, quest sacrifices pleased), blessings and curses (`BlessingService.blessPlayer`/`cursePlayer`). The look comes from the theme's `effects` (`Theme.Effects`, a `Theme.EffectStyle` per `Theme.EffectMood`); config.yml's `effects` switches them (`Settings.Effects.prayerOn()` & co.) and sets the view distance. Rules:
- As grand as the god's rank (`EffectRules.tier`, tested): a spirit's prayers are a modest flicker (scaled-down waves, no symbol) and its sacrifices only particles in the fire; the waves grow with each rank, the floating sacrifice comes at recognized, the symbol at descended, and greater is the grandest. `EffectService.rankUp` is the rank-up effect at the main altar (`EffectRules.rankUp`, grander per rank). The effect switches stay as they are.
- Nearby only: particles and sounds go per player (`Player.spawnParticle`/`playSound` with the sound id string) to players within `effects.view-distance-blocks`; with nobody that close nothing happens at all. Counts are small and fixed (`EffectRules`, tested), particle data is filled per type (dust and color particles get the theme's colors; block and item particles are refused by the loader).
- Display entities (`ItemDisplay`, `TextDisplay`) are spawned through `World.spawn(location, type, setup)` with `setPersistent(false)` set before they enter the world, move by client-side interpolation (`setInterpolationDelay(0)`, `setInterpolationDuration`, a new `Transformation` a tick or more after spawning; rotation steps under 180 degrees), are tracked in `EffectService` and removed when their effect ends, and all of them by `EffectService.stop()` (called by `Gods.stopFeatures`, so on reload and disable). At most `EffectRules.MAX_DISPLAYS` at once. An effect is a few `runTaskLater` steps, never a repeating task; each step checks the display and player are still valid.
- Never reference particles or sounds newer than Spigot 1.21.3 as constants: themes name them, resolved at runtime (`ThemesLoader.Names.particle`/`sound`), unknown ones skipped.

**Ranks (`model/GodRank`, `GodStats`, `service/RankRules`, `RankService`, `command/RankCommand`, `RankLines`):** a religion grows through `SPIRIT` → `RECOGNIZED` → `DESCENDED` → `EXALTED` → `GREATER`.
- Data (gods.yml): `Rank` (missing: never ranked, read as `SPIRIT`), `RankSince`, `Stats.Prayers/Sacrifices/Quests/Converts` (`GodStats`, lifetime counters; other keys under `Stats` are kept), `StatsSeeded`, and `AscendingSince` (since when it has had fewer believers than its rank needs; the old descent key, now for every rank) and `PriestSince`. The counters are counted where things happen, through `RankService.countPrayer` (`PrayerService.handleAltarPray`), `countSacrifice` (a `GOOD` verdict in `CommandmentService.handleSacrifice`), `countQuest` (`QuestService.removeSuccessQuestForGod`) and `countConvert` (an accepted invitation in `PrayerService.believerAccept`). New gods start as spirits with 0 and `StatsSeeded` (`RankService.newGod`, from `GodService.createGod`).
- Conditions (config.yml `ranks.<rank>`, `Settings.RankConditions`, 0/false/null = doesn't count): `min-believers`, `min-power`, `requires-priest`, `min-mood` (a `GodMood` band, at least), `requires-main-altar`, `hours-after-priest` (`PriestSince`), `hours-at-previous-rank` (`RankSince`), and the activity counters `min-prayers`, `min-sacrifices`, `min-quests` (each ignored while its feature is off), `min-altars` (registered praying altars), `min-holy-land-regions` (holy lands, one per altar that claimed land; the key kept its name; ignored while holy land is off), `min-converts`. `requires-priest` and `min-believers` carry over to higher ranks (`RankRules.requiresPriest`, `neededBelievers`).
- `RankRules.evaluate` (pure, tested): one step up when every condition of the next rank holds (`progress`/`qualifies`); mood, activity, power, altars and the main altar never cause a drop (a god stalls); no priest: at once below every rank needing one; too few believers for `ranks.drop-grace-hours`: to the highest rank it still has the believers for. `RankService.evaluate` runs it on the god's turn (`GodUpdateTask`), never while `Storage.cleanupVerdict()` isn't `ALLOWED`.
- Seeding (`RankRules.seed`, tested): the first evaluation of a god without `StatsSeeded` places it on the highest rank whose non-activity conditions (and those of every rank below) it meets, with the time conditions measured against its age (`Created`; unknown counts as old), and sets its counters to `RankRules.requiredStats` of that rank (keeping higher ones). A god with `DescendedTime` keeps at least `DESCENDED`. Seeding is quiet: `GodRankChangeEvent` with cause `SEEDED` (not cancellable), a cancelled `GodDescendEvent` places it at `RECOGNIZED`, only the NPC appears.
- A change (`RankService.change`): `GodRankChangeEvent` (old/new rank, cause `RANK_UP`, `NO_PRIEST`, `TOO_FEW_BELIEVERS`, `SEEDED`, `API`; only `RANK_UP` and `API` can be cancelled, `isCancellable()`; a cancelled rank up is tried again on a later turn), then `GodDescendEvent`/`GodAscendEvent` when it crosses `DESCENDED` (see "God NPCs"), saved at once, floating texts and the chat snapshot refreshed. A rise shows `EffectService.rankUp` at the main altar and the god says `believers-god-rank-up` (`<rank>`; the descent says `believers-god-descended` instead); `GREATER` is broadcast (`broadcast.greater-god`); a fall says `believers-god-rank-down` (falling below descended says `believers-god-ascended`). `RankService.setRank` (the API) bypasses the conditions with the same moment.
- Names: themes.yml `ranks.<rank>` per god type (`Theme.RankNames`, merged per key like `sign`; the default section's names fill gaps): `RankService.getRankName`/`rankName(god, rank)`. Shown in `/g rank [god]` (`gods.rank`; the conditions one per line, `RankLines`, only to the god's believers and the console), `/g info` (the rank; next rank and conditions on one line for believers), `/g list` (`<god-rank>`), the floating text (`<rank>`), PlaceholderAPI `%gods_rank%` (`ChatService.ChatInfo.rankName` off the main thread).
- Unlocks (`ranks.unlocks`, `Settings.Unlocks`, `RankRules.unlocked`, `RankService.hasUnlocked`): `bibles` (/g bible, /g editbible, /g setbible, give-on-join), `quests` (generation in `GodUpdateTask.manageQuests`, `/g prayfor quest`), `holy-artifacts` (the god's gifts in `GodUpdateTask`, `/g holyartifact`), `relations` (starting an alliance or war; ending one always works), `extra-priest` (`RankRules.maxPriests`: `priests.max-per-god` + 1, in `PriestService.managePriests`), `aura` (`RankService.aura` on the god's turn: `ranks.aura`'s effect, ambient, for online believers in their god's own holy land, only while holy land is on; the effect id is resolved through `Registry.EFFECT`, an unknown one warned once), and `holy-land-radius-chunks` per rank (how far each altar's holy land reaches around its altar's chunk, `Settings.Unlocks.holyLandRadiusChunks`, see "Holy land"; the number of holy lands is `RankRules.maxHolyLands`: power / 10 + 3 at every rank, `HolyLandService.getMaximumHolyLandsForGod`). Commands throw `command.rank-locked` through `SubCommand.requireRank(god, rank)`. The features' own settings still apply too (`quests.required-believers` counts online believers, `priests.min-believers` is what a god needs to choose a priest at all); the API's actions bypass unlocks. Sky powers are not gated: each god type's artifact has one fixed power.
- To add a condition: a component of `Settings.RankConditions` and its read in `SettingsLoader.rankConditions` (and `SettingsLoader.RANK_CONDITIONS`), a `RankRules.Condition` with its config key and its check in `RankRules.progress` (an activity counter also goes in `GodStats`, `GodRepository`, `isActivity`, `requiredStats` and a `RankService.count*` where it happens), its default and comment in config.yml, `names.rank-condition.<key>` in messages.yml, and tests in `RankRulesTest`. To add an unlock: a component of `Settings.Unlocks` with its key under `ranks.unlocks` in config.yml (and `TestConfigs.defaultRanks`), then check `ctx.rankService().hasUnlocked(god, ctx.settings().ranks().unlocks().x())` where the feature happens and `requireRank` in its commands.

**Devotion (`model/DevotionLevel`, `service/DevotionRules`, `DevotionService`, `command/DevotionCommand`):** ranks for believers: `FOLLOWER` → `DEVOTEE` → `ZEALOT` → `SAINT`, per believer and their current god.
- Data (believers.yml, see "Models"): `Devotion` points, `DevotionLevel`, `DevotionSince`, `DevotionFaded` (up to when fading was counted). A new entry starts at 0 (`BelieverRepository.getOrCreate`); one without `Devotion` is from before devotion and is seeded once when believers.yml loads (`DevotionService.seedAll`, quiet, no event): `DevotionRules.seed` = prayers to their god × `devotion.points.prayer`, at most the zealot threshold.
- Earning (`DevotionService.earn(believer, god, Deed)`, only for the believer's own god, nothing while `devotion.enabled` is off): `PRAYER` (`PrayerService.handleAltarPray`, a counted prayer), `SACRIFICE` (a `GOOD` verdict in `CommandmentService.handleSacrifice`), `QUEST` (`QuestService.removeSuccessQuestForGod` → `rewardDevotion`: the believers in the quest's `Contributors` (`addContributor` from `handleKilledMob`, `handleSacrifice`, `handleOpenChest`), else the god's believers online), `CONVERT` (`PrayerService.believerAccept`, for `Invitation.By`, set by `/g invite`; the API's invitations have none), `HOLY_FOOD`/`UNHOLY_MOB` (`CommandmentService.handleEat`/`handleKilled`, at most once per `commandment-cooldown-minutes`, kept in memory). Weights: config.yml `devotion.points`.
- Rules (`DevotionRules`, pure, tested): `levelFor` (thresholds `devotion.levels`, each at least one more than the level below, `SettingsLoader`); `evaluate`: up as soon as the points reach a level (several at once), down only below `keepThreshold` (`keep-level-percent` of the level's threshold), then to the level the points reach; `fade`: after `fade-after-days` without a prayer, `fade-percent-per-day` per whole day, compounded, counted once (`DevotionFaded`); `afterLeaving`: `kept-on-changing-god-percent`. Fading and falls run on the god's turn (`DevotionService.update` from `GodUpdateTask`, every believer of the god, online or not); points fade quietly before every change.
- Leaving: `BelieverService.believerLeave` and a change of god in `BelieverService.pray` call `DevotionService.leftGod` (points kept by `afterLeaving`, level what they reach, cause `CHANGED_GOD` about the old god). Removing a believer's entry removes it all.
- A change (`DevotionService.change`): `BelieverDevotionChangeEvent` (old/new level, cause `EARNED`, `FADED`, `CHANGED_GOD`, `API`; only `EARNED` and `API` can be cancelled, a cancelled rise keeps the points), stored (`markDirty`), chat snapshot refreshed; for an online believer a rise is `believer-devotion-level-up` (`<level>`) with `EffectService.devotionUp` (whenever effects are on), a fall `believer-devotion-level-down`.
- Names: themes.yml `devotion.<level>` per god type (`Theme.DevotionNames`, merged per key like `ranks`): `DevotionService.levelName(god, level)`, `getLevelName(believer)`.
- Unlocks (`devotion.unlocks`, `Settings.DevotionUnlocks`): `DevotionService.grants(believer, level)` for bonuses (false while devotion is off) and `allows(believer, level)` for restrictions (true while off). `prayfor-discount` (`prayForCost`, `prayfor-discount-percent`, rounded down, in `PrayForCommand`), `holy-artifacts` (`allows`: the gifts in `GodUpdateTask` and `/g holyartifact`, `command.holyartifact.devotion-locked`; the API bypasses it; zealot by default on purpose: the rarest gift is for believers of weeks), `more-blessings` (`blessingBound`: the item, healing and artifact rolls in `GodUpdateTask` divided by `blessing-chance-multiplier`), `praise` (`DevotionService.praise` on the god's turn, rarely: `believers-devoted-praised` to the others), `title` (`getTitle`: `%gods_devotion_title%`, and before the name in religion chat with `devotion.chat-title`, `chat.titled-player`), `priesthood` (`PriestService.getNextBelieverForPriest` orders candidates by level, then power, `DevotionRules.priestOrder`/`pickPriest`; a candidate of that level is always picked and asked on the god's turn, without the 1-in-3 roll).
- Shown in `/g devotion [player]` (`gods.devotion`; others see level and points, the believer also the next level, fading, what earns points and the unlocks), `/g info` (the believer's own), `/g followers` (`command.followers.devotion`), PlaceholderAPI `%gods_devotion%`, `%gods_devotion_points%`, `%gods_devotion_title%` (`ChatService.ChatInfo`).
- API: `DevotionLevel`, `BelieverInfo.devotion()`/`devotionPoints()` (stored values; reads don't fade), `GodsApi.addDevotion` (cause `API`), `setDevotionLevel` (the level's threshold as points).
- To add a deed: a `DevotionService.Deed`, its weight in `Settings.DevotionPoints`, `SettingsLoader.loadDevotion`, config.yml `devotion.points` (and `TestConfigs.defaultDevotion`), and an `earn` call where it happens. To add an unlock: a component of `Settings.DevotionUnlocks` with its key under `devotion.unlocks`, a line in `/g devotion` (`command.devotion.unlock.<key>`), and `grants`/`allows` where the feature happens.

**Prayer power decay (`BelieverRules.quietPeriod`/`decayOneDay`/`decay`, `BelieverService.decayPrayerPower`, `PrayerService.removeLostBelievers`):** believers who stop praying lose prayer power and leave their religion when it is gone (this replaced `believers.max-hours-without-prayer`, see `ConfigV5ToV6`).
- Quiet period: `believers.decay-after-days` × the believer's devotion level's `decay-after-multiplier` (follower 1, devotee 1.5, zealot 2, saint 3; a follower's while devotion is off), from their last prayer (a wanted sacrifice and an enemy kill count as prayers; a missing last prayer is long ago, an unreadable one is skipped). After it, each whole day takes `decay-percent-per-day` percent (rounded up, so at least 1) and then `decay-per-day`, never below 0; `PrayerPowerDecayed` (believers.yml) is how far it was counted, so each day counts once. A prayer moves the quiet period, which stops the decay.
- Leaving (`Decay.lost`, the user's rule): only when at least one day of decay has passed since the quiet period ended and the power is 0 then (also when it was 0 before). 0 prayer power alone never makes a believer leave: one who prays within their quiet period stays whatever their power. With both decay settings at 0 nobody leaves for not praying. Tested in `BelieverRulesTest`.
- Devotion fades on its own (`devotion.fade-after-days`); the quiet period is that of the level the believer has now, so a neglectful saint who falls to zealot (about nine days with the defaults) has a zealot's quiet period from then on. `GodUpdateTask` runs `DevotionService.update` first, then `removeLostBelievers`, only while `Storage.cleanupVerdict()` is `ALLOWED` (decay included): every believer of the god, online or not, decays quietly; at most `PrayerService.MAX_LOST_PER_TURN` (5) of those at 0 leave per turn, through the old path (the god says `believers-lost-believer`, `PriestService.removePriest`, `BelieverService.removeBeliever` with `BelieverLeaveGodEvent.Reason.INACTIVE`, which drops the entry and its devotion). Reads (`/g devotion`, placeholders, the API) never decay.

**Holy land (`model/ChunkKey`, `HolyLand`, `NeutralLand`, `service/HolyLandService`, `HolyLandRules`, `HolyLandContest`, `listener/HolyLandListener`, `storage/HolyLandRepository`):** only while `holy-land.enabled`; the data layout is under "Models".
- One holy land per altar, a set of chunks. A praying altar claims land when it is built (`AltarService` → `HolyLandService.addAltar`) and when a believer prays at it (`PrayerService.handleAltarPray` → `addPrayer`), both with the altar block and the sign. When the altar block's chunk is free (no land, not neutral) and the god holds fewer than `RankRules.maxHolyLands` (power / 10 + 3) lands, a new land is made (cancellable `HolyLandClaimEvent`, named from the biome, `holy-land.size`), centered on the altar block's chunk; at the limit a builder hears `holy-land.cannot-claim-more`. When the chunk is already that god's land, the land counts as prayed in (`LastPrayerTime`) and grows; another god's land or neutral land is never taken.
- Chunks (`HolyLandRules`, pure, tested): `footprint` (the chunks of the altar block, its sign and the standing spot in front of the sign, `MainAltarRules.standingSpot`: 1 to 4), `square` (radius `ranks.unlocks.holy-land-radius-chunks` of the god's rank around the land's center: spirit 0, recognized 1 = 3x3, descended 2 = 5x5, exalted 3 = 7x7, greater 4 = 9x9) and `claimable` (only free chunks). A land takes them on its claim and on every prayer at an altar in it, so it grows lazily as the god rises; a god that falls in rank keeps its chunks. Growth fires no event.
- A land goes when nobody prayed in it for `holy-land.delete-abandoned-after-days` (`removeAbandonedLands`, per land), with its god (`removeHolyLandsForGod`), and with its last altar: when `AltarRegistry` removes a praying altar (or its sign changes god or kind), `HolyLandService.altarRemoved` removes the land its altar block was in if it is that god's land and no other registered praying altar of the god has its altar block in the land (`HolyLandRules.goesWithAltar`); the god's online believers hear `holy-land.lost-altar`. Lands without a known altar (migrated, never scanned) only go by abandonment.
- Neutral land is per chunk: `/g setsafe` sets the 3x3 chunks around the player (`HolyLandRules.NEUTRAL_RADIUS_CHUNKS`), or clears them when the player's chunk is neutral.
- Attacks (`/g startattack`, `RelationService`, `HolyLandContest`): an attack takes the whole land the priest stands in (the contest state is on the land); winning gives the attacker the whole land. `RelationService.isAttackingHolyLand(god)` checks and clears an attack whose land is gone or settled.
- Protection (`holy-land.protection`: `auto`, `on`, `off`; `HolyLandRules.protects`, `HolyLandService.protects()`, read at use time): `auto` is off while GriefPrevention or WorldGuard is on the server, whose claims and regions protect land, else on (enable and `/g reload` log which). While it is off, `HolyLandListener`'s protection handlers do nothing for holy and neutral land (block place/break/use, PvP and mob damage with `holy-land.lightning`, world mob spawns, explosions, ender pearl and chorus fruit teleports); claims, growth, abandonment, the altar rule, titles on entering (`onPlayerMove` compares block chunks), the aura, ranks and attacks (kills, desecration, time) work as always. Powers never change blocks in another god's holy land or neutral land either way (`NaturePowers.mayChange`).

**Quests:** only PILGRIMAGE, SLAY, ITEMSACRIFICE and GIVEITEMS are generated; the other `QuestType`s stay in the enum because old `quests.yml` files may hold them. Location searches (pilgrimage chests, `PilgrimageSites`) have a hard cap on attempts and on chunks they load: never loop until a spot is found.

**Data rules:** players are keyed by **UUID**; never key data by player name. Never write a raw `UUID` (or any other non-primitive object) into a `YamlConfiguration`: SnakeYAML tags it and Bukkit then refuses to load the file. Store `toString()`.
- Holy books and holy artifacts are recognized by `PersistentDataContainer` tags (`gods:holy_book_god`, `gods:holy_power`, …), never by display name or lore; old untagged items are only a fallback.
- Permission checks go through `ctx.permissions().hasPermission`, which is Bukkit's `Player#hasPermission`. There is no Vault dependency.

**Commands (`command/`):** `CommandRouter` (a `TabExecutor`) handles `/g` (alias `/gods`); each subcommand is its own `SubCommand` class (`<What>Command`), registered in `Gods.registerCommands()`. `/g` alone shows `Overview`. The router finds the command by its first argument (name or alias, ignoring case; unknown: `command.invalid`) and checks, in this order, before `execute(sender, args)` (`args` = what follows the name): the feature is on (`disabledMessage()`, e.g. `command.disabled.marriage`; null when on), the permission (ops have all, players through `ctx.permissions()`, the console through Bukkit; `command.no-permission`), player-only (`command.player-only`), priest-only (the command's own `not-priest` message or `command.priest-only`), believer-only (`command.no-god` or the command's own) and `args(min, max)` (`command.usage` with `command.<name>.parameters`). So a player-only command can cast `sender` to `Player`, and a believer-only one can call `believersGod(player)`. `execute` stops with `throw new CommandException("command.<name>.<reply>", tags…)` (sent to the sender) or `throw new UsageException()`. `/g help` (`HelpCommand`) and tab completion of the first argument list what `router.canUse` allows (feature on, permission, player, priest); `/g help [page]` shows `HelpPages.PER_PAGE` (8) commands a page (`HelpPages`, pure, tested: a number is a page, `altar` and `blocks` are topics, anything else the first page; `command.help.header` knows `<page>`/`<pages>`, `next-page` follows every page but the last, `no-page` for a page past the end); later arguments come from `tabComplete(sender, args)`. Shared helpers are on `SubCommand`: `onlinePlayer(name, notFoundKey)` (exact name, online), `knownBeliever(god, name)` (a god's believer, online or not, without asking Mojang), `onlinePlayerNames`, `believerNames`, `godNames`, `nameOf(uuid)`, `timeAgo`. Commands call services and pass `Player`/`UUID`, never player names. `CommandChecks` is the router's only link to believers and priests, so `CommandRouterTest` runs the router with fake commands and proxy senders; `PluginYmlTest` checks every command's permission is declared and a child of `gods.*`. To add a command:
1. Write `XCommand extends SubCommand`: the constructor calls `super(ctx, "name", "gods.node")` and then `playerOnly()` / `believerOnly()` / `priestOnly(…)` / `args(min, max)` / `aliases(…)` as needed; override `disabledMessage()` if a config switch turns it off, and `tabComplete` for its arguments.
2. Add it to `Gods.registerCommands()`.
3. Add `command.<name>.parameters`, `.description` and its replies to `lang/english/messages.yml` (`MessageKeysTest` checks them).
4. Declare its permission node in `plugin/src/main/resources/plugin.yml` and as a child of `gods.*`.
- `/g admin <action> …` (`AdminCommand`, default op): tools for admins; each action needs its `gods.admin.<action>` (checked inside the command), and any one of them lets the sender use `/g admin` (`AdminCommand.permitted` overrides `SubCommand.permitted`, which the router uses for every command; `gods.admin` gives them all) (`AdminArgs.ACTIONS`/`permission`; declared in plugin.yml with default op, children of `gods.*` and of `gods.admin`, which `PluginYmlTest` checks). Actions: `info`, `setrank`, `devotion`, `prayerpower`, `mood`, `gender`, `godskin`, `quest`, `setaltar`; `/g admin` alone lists those the sender may use (`command.admin.line`). Each calls the service the game and the API use (`RankService.setRank`, `DevotionService.addPoints`/`setLevel` with cause `API`, `BelieverService.increasePrayerPower`, `MoodService.addMoodForGod`, `GodService.changeGender` without the cooldown, `setNpcSkin` through `SkinResolver`, `QuestService.startQuest`/`completeQuest`/`failQuest`, `AltarRegistry.setMainAltar` with `MainAltarRules`), so a cancelled event answers `command.cancelled`; changes are logged. Arguments are read by `AdminArgs` (pure, tested: amounts `20`/`+5`/`-5`, decimals with `=-50`, ranks and devotion levels by key or themed name). Messages: `command.admin.*` (each action's `.parameters`/`.description` are built from the action name, so keep them for every action); `godskin` and `setaltar` reuse `command.godskin.*`/`command.setaltar.*`. A new action: add it to `AdminArgs.ACTIONS`, a case in `execute` and `tabComplete`, its messages and its node in plugin.yml.

**Messages (`message/`, MiniMessage):** no user-visible text belongs in Java code; log and console-only text stays English in code. Everything players see comes from `plugins/Gods/lang/<language>/` (`general.language` in config.yml; only `english` is bundled):
- `messages.yml`: every message that isn't a god's voice, in sections by area (`command.<name>.*` incl. `.parameters`/`.description` for `/g help`, `holy-land.*`, `altar.*`, `prayer.*`, `artifact.*`, `broadcast.*`, `names.*` for item/mob/god type/gender/mood names, …) and `god.speech` / `god.speech-believers`, the formats of a god's words to one player and to its religion (`GodSpeech` picks by the call: `say`, `sayWithQuestion`, `sayText` and the API's `say` are to one player; `sayToBelievers`, `sayToBelieversExcept`, `sayToPriests`, `sayTextToBelievers` and the API's `sayToBelievers` to the religion). A message is one line, a list of lines, or `''` (send nothing).
- `voices/<type>_<gender>.yml` (26 files, e.g. `voices/sun_female.yml`): a god's voice. Each key (a `Voice`, e.g. `believers-slay-quest-started`; the old LANGUAGESTRING name without `GodTo`, kebab case) is a list of lines; the god says one at random; `''`/`[]` says nothing. The voices are picked per god from its type and gender (`GodService.getVoicesForGod`, `GodRules.voices`). Only male and female have files (`GodVoices.name` refuses others): a non-binary god has both of its type's, and `GodVoices.randomLine(voices, situation)` picks the file for each utterance, then a line of it, so everything that reads a god's voice (`GodSpeech.voiceLine`, the API's voice lines, book pages) handles it.
- Both carry `messages-version` (`Messages.MESSAGES_VERSION`, now 2). A key missing from the server's file falls back to the bundled file of the same language, then to the bundled english one (a voice never falls back to another type's voice). Missing bundled files are copied to the server.
- `Messages` (`ctx.messages()`, loaded by `loadData()` on enable and `/g reload`) renders MiniMessage to legacy `§` text: `send(sender, key, tags…)`, `legacy`/`legacyLines`/`component(key, tags…)`, `broadcast(server, key, tags…)`, `parse(miniMessage)`, and the names `itemName`, `mobName`, `godTypeName`, `genderName`, `moodName`. It is thread-safe (the chat thread renders too). Every message knows `<server>` and `<hl>…</hl>` (the gold, not bold highlight the old `$`-placeholders had). Tag helpers: `Messages.text(name, value)` (unparsed), `player`, `god`, `amount`, `type`, `displayName`/`legacyText` (text with `§` colors, e.g. display names), `component`, `color(name, ChatColor)`. **Values from players (names, god names, descriptions, chat) must go in unparsed** through these helpers, never by string concatenation into MiniMessage.
- `GodSpeech` (`ctx.godSpeech()`) is the god's voice: `say`/`sayWithQuestion(god, player, Voice, delay, tags…)`, `sayToBeliever(s)`, `sayToBelieversExcept`, `sayToPriests`; `sayText` makes a god say any MiniMessage text in its style; `voiceLine`/`plainVoiceLine` pick a line (book pages). A god's line knows `<god>` and `<gender>` (its gender's name, `GodService.genderTag`; a line that names the god's title uses it, and lines about the god itself say nothing gendered, because a deity speaks lines of both its type's voices), and `<player>` is the player spoken to unless the call passes one. Every utterance passes `GodSpeech.deliver`, which fires the API's `GodSpeakEvent` (a listener may change the chat line or cancel it, e.g. to show the words through an NPC); `say` and `sayText` return false when the player can't hear or a listener cancelled. `sendInfo(player, key, delay, tags…)` sends a messages.yml message later (`InfoTask`). Every call passes its own tags; there is no shared placeholder state.
- **Adventure rules:** MiniMessage and the legacy serializer are shaded and relocated to `com.dogonfire.gods.libs.kyori` (Spigot has no Adventure). Never pass Adventure objects to Bukkit/Paper API, and never call Adventure methods on Bukkit objects: after relocation they are different classes. Text reaches Bukkit as legacy strings (`Messages.legacy`): chat, titles, item names and lore, book pages, signs, broadcasts.
- To add a message: add the key with a comment listing its tags to `lang/english/messages.yml` and use `send(…, "the.key", …)`. To add a voice situation: add a `Voice` and a list of lines to **all 26** `lang/english/voices/*.yml`. A changed bundled voice line that the old files had too goes in `LegacyLangFilesTest.REWRITTEN_VOICES` (a changed messages.yml text in `REWRITTEN_MESSAGES`): the old bundled files then convert to the new ones except those keys. `MessageKeysTest` checks that every key the code names exists (it scans string literals of the form `"section.key"`), that every command has its parameters and description, and that every `Voice` is in every voice file. New keys reach servers through the bundled fallback; renaming or moving keys needs `MESSAGES_VERSION` + 1 and a migration.
- Old files: `migration/LegacyLangFiles` converts the language files of 0.9.x and of this branch before MiniMessage (`lang/<language>_general.yml`, `lang/<language>_<type>_<gender>.yml`) on every load: each becomes the new file (the bundled one plus every message the old file says differently, converted by `LegacyText`: `&`/`§` codes to MiniMessage, `$PlayerName` & co. to the key's tags, old keys to new ones), and the old file is moved to `lang/old/`. An existing new file is never overwritten. A message equal to one of Gods' own old texts is no change: `plugin/src/main/resources/legacy-lang/<old file>` holds, per old key, every text Gods' own english files ever had (every 0.9.x version, which 0.9.x also downloaded from GitHub, and this branch's before MiniMessage; generated once from the repository's history, never edited by hand), so an unchanged old file keeps nothing. Keys this branch renamed before MiniMessage (the `GiveBibles` quests to `GiveItems`, `GetHolyArtifactThisQuest*`, `AltarPrayingNowAllowed`) carry over through `VOICE_RENAMES`/`INFO_RENAMES`. `LegacyLangFilesTest` converts every stock 0.9.2 file (`legacy/lang/0.9/`) to exactly Gods' own new files.
- Altar signs are recognized by their tags, so the text Gods writes on them is a message (`altar.sign.<style>.<kind>`, see "Altars"); the words of altars from before tags ("Altar / of", "Curses / On", "Blessings / On") still mark those in the world, so they stay in `AltarSigns`. `names.item.*`/`names.mob.*` name every mob and item of the bundled themes (`MessageKeysTest` checks it); anything else gets a name made from its id (`Messages.readableName`: `COOKED_BEEF` is "Cooked Beef"). Old untagged holy artifacts are read by their English lore (`HolyPowerRules.describe`, `HolyArtifactRules.isArtifactLine`), whatever `artifact.*` says now.

**Tasks (`task/`):** short delayed `Runnable`s named `<What>Task` (subclasses of `Task`, which takes the context) scheduled through the Bukkit scheduler (divine effects, messages, mob spawns), and `GodUpdateTask`, the gods' update loop. Repeating ones must end on their own (a stop time, the player logging off); onDisable cancels whatever is left. A task that runs for the life of the plugin belongs in `Gods` (tracked, see lifecycle).

**Integrations (`integration/`):** `GodsPlaceholderExpansion` (PlaceholderAPI, registered only if that plugin is present, unregistered on disable; `%gods_name%`, `name_space`, `color`, `prayerpower`, `rank`, `devotion`, `devotion_points`, `devotion_title` and `tag` (`placeholder.tag`/`tag-priest` in messages.yml, rendered when the snapshot is taken), all from the `ChatService` snapshot (`ChatService.info`: the cached one, on the main thread a fresh one if none is cached); a new placeholder gets a `ChatInfo` field filled in `ChatService.snapshot`), `WorldGuardIntegration` (`ctx.worldGuard()`, null without WorldGuard; regions powers never change) and `GriefPreventionIntegration` (`ctx.griefPrevention()`, null unless GriefPrevention is enabled; claims for `AltarClaims`; either one being there makes `holy-land.protection: auto` leave the protection of holy land to it, see "Holy land"; a `provided` dependency from JitPack, `com.github.GriefPrevention:GriefPrevention`). The NPC providers for Citizens and FancyNpcs are in `integration/npc/` (see "God NPCs"). Each references the other plugin's classes, so only create it when that plugin is there. `GodsMetrics` sends anonymous statistics to bStats (project 35252) with Gods' own charts (`gods`, `believers`, `god_types`, `features`, `language`, `integrations`; the chart ids must match the ones on the bStats project page). bStats asks for chart values on its own thread, so they come from a snapshot `GodsMetrics.refresh()` takes on the main thread (every 5 minutes and after /g reload). bStats is shaded and relocated to `com.dogonfire.gods.libs.bstats`.

**Listeners (`listener/`)** turn events into service calls, one class per area: `HolyLandListener` (protection while `HolyLandService.protects()`, entering land, attacks), `AltarListener` (altar signs, praying/cursing/blessing at altars, sacrifices), `AltarWorldListener` (the altar registry: chunk loads and unloads, blocks that break or move), `BelieverListener` (a believer's death), `MarriageListener` (wedding tokens), `ChatListener` (religion chat, on the async thread through the `ChatService` cache), `GodListener` (commandments on kills and meals, the online gods list on join/quit), `QuestListener` (kills and meals for quests, pilgrimage chests), `HolyBookListener` (reading a holy book) and `HolyArtifactListener` (using one, picking up a second). `GodListener` and `QuestListener` handle meals and share one `ActionCooldown` with `HolyBookListener` (10 seconds; `Gods` owns it), which gives every listener the same answer for the same event. Keep the priorities and `ignoreCancelled` flags when moving a handler, and register a switchable one in `startFeatures`.

**API (`api/` module, `com.dogonfire.gods.api`):** what other plugins compile against. `GodsApi` is registered in Bukkit's services manager by `Gods.onEnable` (`Bukkit.getServicesManager().load(GodsApi.class)`) and implemented by `plugin/…/service/GodsApiService` on top of the services. It reads (`GodInfo`, `BelieverInfo`, `QuestInfo` snapshots, built from the models by `ApiSnapshots`; holy/neutral land; the god's NPC, `getNpc`/`isGodNpc`, default methods), speaks as a god (`say`/`sayToBelievers` with MiniMessage text through `GodSpeech.sayText`; `sayVoiceLine`/`getVoiceLine` with a situation = a `Voice` key, `Voice.byKey`, and placeholders inserted unparsed) and acts as a god (bless, curse, heal, give items/artifacts, smite, mood, gender (`setGender`, which skips the priests' cooldown but starts one), prayer power, quests, invite, priests, alliances and wars), returning an `ActionResult`. Events are in `api/event` (`GodEvent` carries the god's name; `QuestEvent` a `QuestInfo`).
- **Rules:** public signatures may only use Java, Bukkit and `api` types (`ApiSurfaceTest`): never model, service or Adventure types (Adventure is relocated in the jar). Text goes in and out as plain strings: MiniMessage in, legacy `§` text out. Snapshots are immutable records (copies of lists and `Location`s). The API's enums (`GodType`, `GodGender`, `GodMood`, `GodRank`, `DevotionLevel`, `QuestType`) are its own; `ApiSnapshots` maps the model's to them, and `ApiSnapshotsTest` checks every constant maps. Keep it backwards compatible: add methods (with a `default` when an overload will do), record components only at a major version or at the end with the old constructor kept (as `GodInfo.mainAltar`, `GodInfo.descended`, `GodInfo.rank` and `BelieverInfo.devotion`/`devotionPoints`; `ApiSurfaceTest.snapshotsKeepTheirOldConstructors`), enum constants freely; never rename or remove. Everything is main thread only (`GodsApiService.checkThread`). Reads must not change anything (e.g. snapshots read the stored priest list, not `PriestService.getPriestsForGod`, which leaves out inactive priests).
- **Actions** call the same service methods as commands and the update loop, so effects, messages, saves and events are the same; if a command did the work itself, move it into the service first (as with `PrayerService.invite`, `PriestService.offerPriesthood`, `RelationService.setAlliance`/`setWar`, `QuestService.completeQuest`/`failQuest`). A service method that fires a cancellable event returns false (or a result) when it is cancelled, so the API can answer `CANCELLED` and commands `command.cancelled`.
- **Events** are fired from the services (never from commands or listeners) through `ctx.fire`, so every way into the change fires them. A cancellable event is fired before anything changes; a cancelled one changes nothing. One that reports something done (`BelieverLeaveGodEvent`, `PriestRemoveEvent`, `QuestCompleteEvent`, `QuestFailEvent`) isn't cancellable.
- **To add an API method:** declare it on `GodsApi` with javadoc saying what it returns when (doclint checks the javadoc), implement it in `GodsApiService` (`checkThread()`, `existing(godName)` for the god, then a service call), and add a test if part of it runs without a server.
- **To add an event:** a class in `api/event` extending `GodEvent` (or `QuestEvent`), with `HANDLERS`/`getHandlers`/static `getHandlerList`, `Cancellable` if the change can be stopped; fire it from the service that makes the change and handle a cancel there (commands then throw `CommandException("command.cancelled")`); add it to `ApiSurfaceTest.API` and to the README's list.
